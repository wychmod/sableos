SableOS 是一个企业能完全掌控的、Java 原生的、私有可审计的 Agent OS。 它装在企业自己的 K8s、服务器或物理机上，作为统一底座运行各类业务 Agent—— 共享一套渠道接入、模型路由、记忆系统、工具调用与安全审计。 业务方不写 Agent 后端代码，只需要配置 Agent、编写 Tool。

为什么需要 SableOS

Agent 大多停在 demo，卡在四道门槛上

SableOS 一次拆掉这四道门槛。更深一层的判断是：让 Agent 在生产环境可靠工作的瓶颈，通常不在模型本身，而在 Agent 的运行环境。

门槛 01

定义 Agent 要写代码

最懂业务的人反而做不了，需求和技术之间隔着一条开发排期

一个目录 + 一份 AGENT.md 就是一个 Agent，无需写代码

门槛 02

数据要被云平台拿走

合规过不去，敏感业务根本没法上

私有部署，数据不出域，不锁任何云生态

门槛 03

执行是个黑盒

没有审计、没有白名单、没有审批，企业不敢上生产

强制沙箱 + 全链路审计，安全从第一天就在架构里

门槛 04

跑一个容易，跑一群难

缺一层管理「一群 Agent 的操作系统」

为一整队 Agent 准备的生命周期与治理

生态分层

SableOS 守住「运行时」这一层

框架给你代码、要你自己搭运行环境；编排平台给你流程、跑在运行时之上；SableOS 给的是运行时本身。

框架层

Spring AI、LangChain4j 等。提供 Provider 抽象、Tool schema 生成等代码积木。

运行环境、推理循环、工具治理、审计仍需自建

编排平台层

Dify、Coze 等。提供可视化流程编排，跑在某个运行时之上。

私有化与合规受限，代码级扩展受限

运行时层 · SableOS

让 Agent 能常驻、可治理、可审计地跑起来的底座，原生对接 MCP、A2A 等开放协议。

你只需要写业务 Tool，其余交给底座

为什么必须是 Java

业界已验证的两个开源 Agent OS——Node.js 的 OpenClaw、Python 的 Hermes Agent——都不是 Java。而 Java 是大量企业后端的事实标准：Spring Boot 与 Nacos、Sentinel、SkyWalking、Prometheus 等运维体系可直接复用；Tool 能直接调企业现有 Java 服务；严监管行业的私有部署与合规审计能走现有流程。

运行时内核

五大核心能力

引擎与能力之间、能力与外部之间都通过抽象接口解耦。扩展阶段加新 Channel、新 Provider、新 Tool，只需在边缘扩展，不动核心引擎。

对接 LLM

Provider 抽象统一对接主流大模型与本地推理（Ollama、vLLM 等）。多 Provider 通过显式映射并存，运行时切换无锁定。

ReAct 循环

自实现的推理引擎：LLM 决定调不调工具、调哪个，执行后回填结果继续推理，直到给出最终响应或达到最大迭代次数（默认 10）。

Memory 记忆

统一门面提供会话记忆与长期记忆。长期记忆默认落 .sableos/memory/MEMORY.md，后端可插拔（Markdown / SQLite / 自托管 Mem0）。

Tool 体系

九个内置 Tool 加 Plugin Tool 三档接入；MCP Client 对接外部工具。文件、Shell、HTTP 与通知类调用经 Sandbox 白名单校验，全部调用落 tool_invocations 审计。

Web Service

所有能力经 REST API 对外暴露，核心阶段 10 个端点。业务系统用任何语言经 HTTP 接入。

三条演进主线

单机运行时内核 → 底座分布式 → 跨节点 Agent 协作。横向能力（多租户、SSO、完整审计查询、可观测）伴随各阶段补齐。

核心特性

九条产品主张

从定义方式、部署形态到安全边界，逐条对应设计原则。

一个目录 = 一个 Agent

一个包含 AGENT.md 的目录定义一个 Agent，不用写代码，多个 Agent 在同一实例并存。

Java 原生

基于 JDK 21 与 Spring Boot 3.x，单可执行 JAR 部署，复用企业现有的 Java 运维工具链。

私有可控

装在企业自己的 K8s、虚拟机或物理机上，数据不出域，不锁任何云。

安全隔离

工具调用经文件、命令、网络白名单校验，强制沙箱隔离，凭证走企业密钥体系不落地，全链路可审计。

自实现 ReAct

核心推理循环自己实现，不套外部 Agent 框架，机制完全可控。

对接开放标准

工具用 MCP、Agent 协作用 A2A、Agent 目录借 Anthropic Agent Skills 的形态，与生态协同而不另立协议。

三档工具扩展

零代码 Agent 目录加复用 MCP、轻代码自写 MCP server、重代码原生 Java 方法，按门槛自由选择。

跨对话记忆

会话加长期两层记忆，长期记忆后端可插拔，让 Agent 记得住偏好与关键事实。

无状态可扩展

运行实例无状态、状态外置，从架构起为分布式演进留好路。

架构

一次消息的处理链路，分四层

技术栈一句话：JDK 21 + Spring Boot 3.x + Spring AI Alibaba + 自实现 ReAct loop + SQLite + Picocli。

L1接入层

CLI Channel Web Service（REST API） AgentScheduler（cron 定时触发）

L2引擎层

AgentService（统一入口） ReActLoop（自实现） PromptBuilder ToolExecutor

L3能力层

ProviderService MemoryService ToolRegistry + Sandbox KnowledgeService NotifyChannel

L4基础层

SQLite（Session / tool_invocations / llm_calls） .sableos/ 文件系统

工程结构 · Maven 多模块

以《技术方案》第 10 章为准，目标是 14 个模块；当前骨架已落地 9 个。
模块职责状态
sableos-core核心抽象与接口：SableTool、Profile、ContextLoader、ReActLoop、PromptBuilder、ToolExecutor、AgentService、AgentScheduler骨架
sableos-providerProvider 服务、Function Calling 适配、provider name 到 ChatModel 的显式映射骨架
sableos-memory记忆统一门面、长期记忆、save_memory / recall_memory 工具骨架
sableos-tool内置 Tool、MCP Client、ToolRegistry、Sandbox 与通知适配器（三合一）骨架
sableos-storage持久化层：Session、Tool 调用与 LLM 调用审计落库骨架
sableos-webWeb Server、六个 ApiController、OpenAPI 文档骨架
sableos-cli命令行入口：Picocli、ConfigLoader骨架
sableos-channel-cliCLI Channel：sableos chat 交互对话骨架
sableos-bootSpring Boot 启动模块：主类、自动配置、依赖聚合骨架
sableos-persona人格库：内置人格预设加自定义人格 CRUD规划
sableos-knowledge知识库：解析 / 切分 / 向量化流水线，双路召回加 RRF 融合检索规划
sableos-channel-feishu飞书入站渠道：长连接收事件、出站过沙箱、自动重连规划
sableos-channel-wecom企微入站渠道（对称飞书）规划
sableos-channel-dingtalk钉钉入站渠道（对称飞书 / 企微）规划

模块之间通过接口解耦

扩展阶段加新 Channel 或新 Tool 实现，只加新模块，不改 core。

快速开始

四条命令，从零到一个能对话的 Agent

需要 JDK 21 或更高、Maven，以及一个 LLM Provider——云端 API，或本地 Ollama / vLLM 等 OpenAI 兼容服务。

  1. 1

    构建

    产出可执行 fat JAR。骨架阶段即可验证。

  2. 2

    初始化工作区

    创建 .sableos/ 目录结构。

  3. 3

    生成一个 Agent 目录

    得到 .sableos/agents/weather-bot/AGENT.md。

  4. 4

    对话，或对外服务

    本地 CLI 交互，或启动 REST API 与 Swagger UI（默认端口 8080）。

bash 
# 1. 构建：产出可执行 fat JAR
mvn clean package

# 2. 初始化工作区
sableos init

# 3. 生成一个 Agent 目录
sableos profile create weather-bot

# 4. 交互对话
sableos chat

# 5. 启动 Web Service：REST API 与 Swagger UI
sableos serve

一个最小 AGENT.md

AGENT.md 
name: weather-bot
description: 每天早上播报天气并给出穿搭建议

identity:
  agent_name: 天气助手
  prompt: 你是天气播报助手，关注用户所在城市的天气变化

provider:
  name: deepseek
  model: deepseek-chat
  temperature: 0.7

tools:
  - http_get
  - notify

settings:
  max_iterations: 10
  max_history_turns: 20

正文写任务指令，frontmatter 是这个 Agent 的运行配置（派生成 Profile）。 Skill 绑定通过 Agent 目录下 skills/ 的相对软连接表达，不写进 frontmatter。

tree

设计原则

七条不妥协的约束

这些原则写进了项目宪章，也是评审每一次架构升级的标尺。

01

底座优先于 Agent

最重要的交付不是某个强大的 Agent，而是让任意 Agent 都能可靠运行的环境。

02

配置即 Agent

一个 Agent 由一份配置定义，而不是由代码写出。

03

自实现核心，可控优先

核心推理循环自己实现，底层模型协议适配复用成熟库，不重复造轮子。

04

对接开放标准

工具用 MCP、协作用 A2A、技能用开放格式，与生态协同。

05

无状态实例，状态外置

从单机平滑走向分布式的前提。

06

安全是地基不是补丁

工具来源受控、最小权限、强制沙箱、凭证不落地、全链路可审计。

07

分阶段克制

当前只做运行时内核的最小完备集，每次架构升级都用真实使用数据证明其必要性。

路线图

慢就是快，克制且聚焦

先把单机的运行时内核做扎实，让一个节点上运行和管理一群 Agent 真正可用，再在它之上逐步生长出分布式能力。

当前

阶段一 · 单机运行时内核

  • 五大核心能力跑通
  • 配置即 Agent、多 Agent 并存
  • REST API 接入、对接 MCP
  • 把单节点运行和管理一群 Agent 做到可用
规划

阶段二 · 底座分布式

  • 节点无状态化
  • 状态外置、多副本部署
  • 支撑更大规模与高可用
愿景

阶段三 · 跨节点 Agent 协作

  • 引入 Agent 通信底座
  • 对接 A2A 协议
  • 多节点上的 Agent 跨节点发现、委托、可靠异步协同

横向能力 · 伴随各阶段逐步补齐

多租户、SSO、完整审计查询、Tool 治理、可观测与 Web 管理台。

生态与标准

与生态协同，而不另立协议

能复用的协议一律复用，只把力气花在别人没做的那一层。

MCP

Model Context Protocol：LLM 与外部工具、数据源连接的开放协议，工具生态的事实标准。

工具接入层

Agent Skills

Skill 的开放目录格式，SableOS 的 Agent 目录借其形态。

Agent 定义形态

Spring AI

LLM Provider 抽象与主流模型 connector，SableOS 的底层 LLM 调用层。

模型接入层

Spring AI Alibaba

面向国内模型生态的 Spring AI 实现，提供主流大模型 connector。

模型接入层
