# Feature Specification: 定时任务调度——让 Agent 到点自己干活（第三种触发源）

**Feature Branch**: `009-lesson25-scheduler`

**Created**: 2026-10-29

**Status**: Draft

**Input**: User description: "第25节需求：定时任务模块——让 Agent 不用人推、到点自己干活（第三种触发源）"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 到点自动触发，走与人推完全相同的入口 (Priority: P1)

运营人员在一个 Agent 的运行声明里写上"每天 08:00 说这句话"。进程启动后，到点由系统自己拼出这条消息，交给与终端对话、HTTP 接口完全相同的处理入口；Agent 完成一次完整的推理与工具调用，产生的模型调用与工具调用审计与人推触发一模一样，无需任何额外配置。

**Why this priority**: 这是本特性存在的理由——没有它，日报、巡检、每日天气这类场景只能靠人天天手动触发。触发之后的一切（推理、工具、审计、会话）都必须复用既有链路，否则就成了第二套运行时。

**Independent Test**: 用一条可由测试直接驱动的触发，断言：注册时下发的规则包含配置里的 cron 与时区；触发后统一处理入口收到配置里的消息文本；两轮定时触发取得同一个会话。

**Acceptance Scenarios**:

1. **Given** 某 Agent 的运行声明含两条定时配置（各自的标识、cron、时区、消息），**When** 系统启动注册，**Then** 两条配置都按"配置里的 cron + 配置里的时区"注册到调度器，没有任何一条使用服务器默认时区。
2. **Given** 某 Agent 配了一条定时任务，**When** 到达触发时刻，**Then** 系统以渠道 `scheduler`、用户 `scheduler`、Agent 名三元组取回或新建会话，并把配置里的消息交给统一处理入口。
3. **Given** 同一 Agent 的定时任务已触发过一次，**When** 下一次触发到来，**Then** 取到的是同一个会话（历史自然累积，靠既有历史轮数上限截断兜底）。
4. **Given** 定时触发跑完一次完整推理，**When** 查看审计，**Then** 本次链路产生的模型调用与工具调用记录与手动触发时完全同形，不出现为定时触发单开的记账口径。

---

### User Story 2 - 上一次没跑完，本次触发直接跳过 (Priority: P2)

一个任务单次执行耗时超过了触发间隔。触发点再次到达时，系统识别到该任务仍在执行，于是直接跳过这一次，不排队等它、不并发跑两份；其它任务不受影响，各自照常触发。

**Why this priority**: 没有这层保护，长任务会自我叠加，模型调用与工具执行随之翻倍，既费钱又会把会话历史搅乱。

**Independent Test**: 人为占住某任务的执行权后触发一次，断言统一处理入口零调用；释放执行权后再触发，断言正常进入。

**Acceptance Scenarios**:

1. **Given** 任务 A 的执行权已被占住（模拟上一次尚未结束），**When** 触发任务 A，**Then** 本次触发被跳过，统一处理入口零调用，且跳过这件事留下可查的日志。
2. **Given** 任务 A 正在执行，**When** 触发任务 B，**Then** 任务 B 正常执行，不被任务 A 拖住。
3. **Given** 任务 A 的上一次已经结束，**When** 再次触发，**Then** 正常执行（跳过不是永久性的）。

---

### User Story 3 - 单次失败不拖垮调度器，且不留死锁 (Priority: P3)

某次定时任务执行中途抛出异常。这一次以失败结束、留下错误日志，调度器本身继续存活，其它任务的下一次触发照常进行；出问题的那个任务在下一次触发点时也能正常进入——执行权在失败后已被释放。

**Why this priority**: 失败隔离决定了这套机制能不能长期无人值守地跑；"失败后锁没放掉"是这类实现最典型的隐性 bug，必须由可执行的断言守住。

**Independent Test**: 让统一处理入口抛异常，断言触发不外抛；紧接着再触发一次，断言统一处理入口被调用第二次（证明执行权确实被释放）。

**Acceptance Scenarios**:

1. **Given** 统一处理入口对某个任务抛出运行时异常，**When** 触发该任务，**Then** 异常不外抛，错误日志包含任务标识与失败原因。
2. **Given** 上一次触发以异常结束，**When** 再次触发同一任务，**Then** 能正常进入并调用统一处理入口（执行权已释放，未永久卡死）。

---

### Edge Cases

- 某 Agent 没有任何定时配置：启动注册时不产生任何任务，也不报错。
- 两个 Agent 声明了相同任务标识：执行权按任务标识划分（同一标识视为同一任务的重叠保护），但会话仍按各自 Agent 名分开（定时会话身份含 Agent 名）。
- 同一 Agent 的两条定时任务同时到点：两次都必须执行，但对共享会话的读写必须串行——后到者等待前一次结束，不得跳过、不得并发改写。
- cron 表达式非法或时区标识非法：注册该条时报错并留下日志；不得让一条坏配置阻断其余任务或整个进程启动。
- 定时配置的消息内容为空：仍按配置触发（消息内容由配置负责，调度模块不改写、不校验语义）。
- 进程在任务执行中途退出：不做补偿、不做恢复（核心阶段任务状态不落库，归第 28 节）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 在启动注册时遍历全部已注册 Agent 的运行声明，把其中每一条定时配置逐条注册到调度器；触发规则完全来自配置，不得写成编译期常量。
- **FR-002**: 每条定时配置 MUST 包含四要素：任务标识、cron 表达式、时区、到点发给 Agent 的消息内容。
- **FR-003**: cron 表达式与时区 MUST 一起生效：任务按配置声明的时区解释，不得回落到服务器默认时区。
- **FR-004**: 同一任务标识的上一次执行未结束时，本次触发 MUST 直接跳过，不排队、不并发；跳过 MUST 留下可查日志。不同任务之间 MUST 互不阻塞。
- **FR-005**: 触发时 MUST 以固定三元组（渠道 `scheduler`、用户 `scheduler`、该任务所属 Agent 名）取回或新建会话，并调用与终端/HTTP 触发完全相同的统一处理入口；同一 Agent 的历次定时触发 MUST 复用同一会话。
- **FR-006**: 单次执行抛出的任何异常 MUST 不外抛、不中断调度器、不阻塞其它任务；失败 MUST 留下包含任务标识与原因的日志。
- **FR-007**: 无论成功或失败，任务执行权 MUST 在结束时释放，后续触发能再次进入。
- **FR-008**: 定时触发链路上的模型调用与工具调用审计 MUST 与现有人推入口完全一致，不得为定时触发新增记账路径。
- **FR-009**: 定时触发 MUST 作为独立链路进入处理入口：每次触发开一条新的链路标识，跳过分支同样单独成链，不得复用上一次执行的链路标识。
- **FR-010**: 单条定时配置注册失败（cron / 时区非法等）MUST 只影响该条配置，不阻断其余配置注册与进程启动。
- **FR-011**: 同一 Agent 的多条定时任务共享同一会话（FR-005）；系统 MUST 串行化这些触发对该会话的读取与保存，不得出现两个触发各自加载历史、后写覆盖前写而导致历史丢失。

### Key Entities

- **定时任务声明**：Agent 运行声明中的一条定时配置，四要素为任务标识、cron 表达式、时区、消息内容；定义来源唯一，即 Agent 的运行声明。
- **任务执行权**：按任务标识划分的进程内互斥权，仅用于防重叠；不跨进程、不持久化。
- **定时会话**：渠道与用户固定为 `scheduler`、Agent 名为所属 Agent 的会话，与人推会话共用同一套会话存储与历史截断规则。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 一个只写了定时配置的 Agent，无需改任何代码、无需重新编译，进程启动后即到点自动发起完整对话（可由真实验收项确认）。
- **SC-002**: 单次执行时长超过触发间隔时，任意相邻两次执行不重叠——统计一段时间内的并发执行次数恒为 0。
- **SC-003**: 任意单次定时任务失败后，调度器继续工作：其后其它任务的触发次数与配置的 cron 次数一致，且失败任务自身在下一个触发点仍能进入。
- **SC-004**: 同一 Agent 的两次定时触发落到同一条会话记录上（会话总数不因触发次数增长）。
- **SC-005**: 定时触发与手动触发产生的审计记录结构完全一致（同表、同字段、同计数口径）。
- **SC-006**: 同一 Agent 的两条定时任务同时到点（或长任务重叠）时，两次执行都完成，且会话历史同时包含两次的对话——无覆盖丢失。

## Assumptions

- 核心阶段为单实例部署，防重叠只需进程内互斥，不做跨实例协调（分布式协调、选主、租约归扩展阶段）。
- 定时定义只写在 Agent 的运行声明里，改 cron 需要重启（核心阶段口径）；通过接口增删改任务、任务状态与执行历史落库、运行期动态注册/注销单个 Agent 的定时任务分别归第 28 / 30 节，本节不做。
- 只支持标准 cron 表达式 + 显式时区，不支持固定间隔、一次性延时等其它时间表达形式。
- 失败后不做自动重试、不做失败次数告警。
- 调度能力由所用运行框架自带（cron 触发器 + 可动态注册任务的调度器），不引入第三方调度框架；不新增数据表、不新增对外接口。
- 复用前序节已交付的：Agent 运行声明及其定时字段、Agent 运行配置注册表、统一处理入口、会话身份与持久化、链路标识传播工具。
- 定时任务只在常驻模式下运行（`serve` / `gateway`），交互式 `chat` 不启动定时调度。
