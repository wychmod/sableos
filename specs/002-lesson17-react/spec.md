## Clarifications

### Session 2026-10-14

- Q: 历史截断的默认上限"20 轮"（max_history_turns）里，一个"轮"怎么计量？ → A: 一条对话消息 = 一轮（保留最近 N 条消息：用户消息、模型输出、工具结果各计一条）。
- Q: 循环转满最大轮数强制收尾时，返回给调用方的终止结果包含什么？ → A: 固定终止文案（含"达到最大轮数"字样），不拼接最后一条模型输出——与课件骨架 `return "达到最大轮数，已停止"` 逐字一致。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 自主多轮循环：想一步、做一步、看结果，直到把事办成 (Priority: P1)

用户向某个 Agent 提出一句需要外部信息才能回答的话（例如"看看今天天气，帮我决定穿什么"）。系统按固定顺序组装本轮要发给模型的内容、调一次模型；模型这轮若提出要调用某个工具，系统就执行该工具、把结果回填进对话历史，再进入下一轮；直到某一轮模型不再提出调用工具，就以它这一轮的输出作为最终答复收尾。

**Why this priority**: 这是 ReAct 存在的理由本身——把"想—做—看"串成循环。没有它，SableOS 只是一个单轮 chatbot；后面所有关于兜底、审计、编排的要求都无处依附。它是整个能力的 MVP。

**Independent Test**: 用一个可控的模型桩，第一轮返回"要调用某工具"、第二轮返回普通文本；断言工具被执行了一次、结果进入下一轮可见、最终答复就是第二轮模型输出。

**Acceptance Scenarios**:

1. **Given** 一条用户消息，**When** 模型第一轮直接给出最终文本、未提出任何工具调用，**Then** 系统立即以该文本收尾，不再发起第二轮模型调用。
2. **Given** 一条用户消息，**When** 模型第一轮提出要调用工具，**Then** 系统执行该工具、把结果回填进对话历史，并在下一轮把这结果一并提供给模型。
3. **Given** 模型一轮响应里提出了多个工具调用，**When** 系统处理该轮，**Then** 这些工具按顺序逐个执行（不并行），每个结果都回填。

---

### User Story 2 - 循环可控：转得起来，也停得下来 (Priority: P2)

模型可能反复要求调用工具、迟迟不给最终答复；会话历史也可能越滚越长把上下文撑爆。系统必须有两个兜底：迭代有上限（默认 10 次、可由该 Agent 的运行配置覆盖），转够即强制收尾并给出可识别的终止结果（含"达到最大轮数"字样的固定文案）；进入模型的上下文只保留最近 N 条对话消息（默认 20，一条消息计一轮），超出部分丢弃，系统提示始终保留。

**Why this priority**: 这是循环最容易出事的两处。"不兜底"会让 Agent 卡死在死循环里，"不截断"会让上下文越滚越大直至调用失败。两者都是设计时就得定死的边界，而非事后补丁。

**Independent Test**: 让模型桩每轮都提出工具调用（永不收敛），断言模型恰好被调用"上限"次后循环停止并返回终止结果；构造超长历史，断言进入模型的内容只含最近 N 轮。

**Acceptance Scenarios**:

1. **Given** 模型每轮都要求调用工具、永不收敛，**When** 循环运行，**Then** 模型恰好被调用声明的最大轮数次，之后强制收尾并返回可识别的终止结果（一轮不多、一轮不少）。
2. **Given** 某个 Agent 覆盖了最大轮数（不等于默认值），**When** 循环运行，**Then** 以该 Agent 声明的值为准。
3. **Given** 会话历史已超过 N 条消息，**When** 组装本轮上下文，**Then** 进入模型的内容只含最近 N 条对话消息，系统提示仍在。

---

### User Story 3 - 过程留痕可审计：每轮痕迹进会话，每次工具调用进审计 (Priority: P3)

一次处理跨越若干轮，每轮模型的输出和每次工具的执行结果都必须累积进这次会话的对话历史——这样事后能完整回看这次 Agent 到底做了什么，下一轮也接得上；同时每次工具调用不论成功还是失败都要落一条审计记录（工具名、入参、结果、成败、失败原因、耗时、所属会话、链路标识、调用时间），失败带原因、异常不吞。

**Why this priority**: "私有可审计"是 SableOS 的定位；且失败留痕与"累积不全"是最容易漏的两条——漏了累积，下一轮就接不上前一轮；只记成功不记失败，一次真实事故在系统里完全没痕迹。

**Independent Test**: 驱动一次两轮工具调用，断言会话历史里按序保留了每一轮的模型输出与工具结果；分别驱动成功与失败的工具调用，断言审计两条都在、失败那条带原因。

**Acceptance Scenarios**:

1. **Given** 一次包含工具调用的多轮处理，**When** 处理结束，**Then** 会话历史里按顺序完整保留了每一轮的模型输出与每一次工具结果。
2. **Given** 一次成功的工具调用，**When** 执行完成，**Then** 审计新增一条成功记录，含工具名、入参、结果、耗时、会话与链路标识。
3. **Given** 一次失败（工具抛异常或模型给出未注册的工具名）的工具调用，**When** 处理该轮，**Then** 审计新增一条失败记录且带失败原因，异常被收敛为失败结果回填、循环继续、由轮数上限兜底。

---

### User Story 4 - 统一编排与上下文来源：一个入口、一次处理、上下文即时生效 (Priority: P4)

三种触发源（命令行、Web、定时）最终都调用同一个处理入口。入口负责：取当前 Agent 的运行配置、把它放入一个**线程级**上下文（供工具执行时按"当前是哪个 Agent"取值）、跑完循环后把会话保存、并在 `finally` 里清理该上下文——异常路径也必须清。另一方面，组装上下文所依据的 Agent 定义正文、启动信息（Bootstrap）与 Agent 绑定的 Skill 说明，每次组装时都重新读文件、不缓存；显式引用但缺失的 Skill 绑定必须报错，缺失的 Bootstrap 至少记 WARN，绝不静默跳过。

**Why this priority**: 没有统一入口，三种触发源会各写一套编排，必然漂移；线程级上下文不清是"单请求测试永远测不出、并发复用时串号"的最阴险一类 bug。上下文即时生效与"缺失不静默"则守住"人格悄悄丢了"这种最难查的软故障。相对前三个故事，它是最外层的编排与来源治理，故排最后。

**Independent Test**: 处理过程中断言线程级上下文能取到当前 Agent 配置、处理抛异常后它也被清空、处理结束后会话被保存；改一次 Agent 定义/启动信息文件，断言下一次组装立即读到新内容；断言 Skill 绑定缺失时报错、Bootstrap 缺失时 WARN。

**Acceptance Scenarios**:

1. **Given** 一次处理正在进行，**When** 在处理过程中读取线程级上下文，**Then** 能取到本次处理所属 Agent 的运行配置。
2. **Given** 处理过程中抛出异常，**When** 异常向上抛给调用方后，**Then** 线程级上下文已被清空（下一个复用该线程的请求取不到上一个 Agent 的配置）。
3. **Given** 一次处理正常结束，**When** 处理返回，**Then** 这次会话已被保存。
4. **Given** 某个 Agent 的定义正文/启动信息/Skill 说明文件被修改，**When** 下一次组装上下文，**Then** 立即读到新内容（无缓存残留）。
5. **Given** Agent 显式绑定了一个缺失的 Skill，**When** 组装上下文，**Then** 系统报错并点名；**Given** 引用的启动信息缺失，**When** 组装上下文，**Then** 至少记录 WARN，且不静默跳过。

---

### Edge Cases

- 模型连续多轮要求调用工具且永不收敛：达到轮数上限强制收尾，返回可识别的终止结果。
- 模型返回一个未注册（解析不到）的工具名：按失败处理、带原因落审计并回填，循环继续，由轮数上限兜底。
- 一轮响应里含多个工具调用：按顺序逐个执行，不并行。
- 工具执行过程中抛异常：收敛为失败结果（带原因），不吞异常式静默、不中断整个循环。
- 会话历史远超上限：只保留最近 N 轮；系统提示与当前用户消息不因截断而丢失。
- 未配置长期记忆来源：跳过记忆段，不报错、不影响调用。
- Agent 绑定的 Skill 缺失（软连接断裂）或引用的启动信息文件缺失：分别报错 / 至少 WARN，不静默跳过。
- 处理过程中抛异常：会话保存虽被跳过，但线程级上下文仍必须被清理。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 给定一次会话与一条用户消息，系统必须按固定顺序组装本轮要发给模型的内容，并发起一次模型调用；模型本轮未提出工具调用时，以该输出作为最终答复收尾，不再发起下一轮。
- **FR-002**: 模型本轮提出工具调用时，系统必须逐个执行这些工具，把每个结果回填进对话历史，再进入下一轮；工具的执行权唯一收敛在工具执行器一处，底层模型接入层绝不自行执行任何工具。
- **FR-003**: 一轮响应里包含多个工具调用时，系统必须按顺序逐个执行，不做并行。
- **FR-004**: 循环必须设有迭代上限（默认 10 次，可由该 Agent 的运行配置覆盖）；达到上限即强制结束，并返回可识别的终止结果（含"达到最大轮数"字样的固定文案，不拼接最后一条模型输出），绝不无限循环。
- **FR-005**: 每一轮都必须把模型输出与工具结果累积进本次会话的对话历史；累积后既保证事后可审计，也保证下一轮能接上前一轮。
- **FR-006**: 本轮上下文必须按固定顺序组装：系统提示（角色设定 + 启动信息 + Skill 说明，末尾附当前日期时间）→ 长期记忆（未配置则跳过该段）→ 会话历史（只保留最近 N 条对话消息，默认 20，一条消息计一轮）→ 当前可用工具列表。
- **FR-007**: 历史截断只作用于对话历史，不得截断系统提示与当前用户消息；截断后循环仍能正常运行。
- **FR-008**: 工具执行器必须按工具名从工具集合中解析出目标工具；解析不到（模型给出未注册的工具名）时按失败处理并回填，不中断循环，由轮数上限兜底。
- **FR-009**: 每次工具执行前必须经过一道"对外动作白名单校验"的调用位（具体规则属后续 Sandbox 能力，本次仅保留校验位并标注接线处）；执行结果必须被包装成带成功标识的结果（失败时带失败原因），异常不得被吞掉。
- **FR-010**: 每次工具调用不论成败都必须落一条审计记录（`tool_invocations` 表）：工具名、入参、结果、成功标识、失败原因、耗时、所属会话、链路标识、调用时间；失败记录必须带原因。
- **FR-011**: 系统必须提供统一处理入口，三种触发源（命令行、Web、定时）复用同一入口；入口负责取当前 Agent 的运行配置、把它放入线程级上下文、跑完循环后保存会话、并在 `finally` 清理线程级上下文（异常路径同样清理）。
- **FR-012**: 线程级上下文承载"本次处理所属 Agent 的运行配置"，供工具执行时按当前 Agent 取值；有效期为一次处理；由于每请求独占一个虚拟线程，天然不串台。
- **FR-013**: 组装上下文所依据的 Agent 定义正文、启动信息与 Agent 绑定的 Skill 说明，每次组装时都必须重新读取、不做缓存；Agent 定义正文与启动信息全量注入；Skill 只注入其名称、描述与本地读取路径，Skill 正文不预载。
- **FR-014**: Agent 显式引用但缺失的 Skill 绑定必须报错并点名；缺失的启动信息至少记录 WARN；两者都不得静默跳过。
- **FR-015**: 本次交付的会话保存在进程内承载（跨重启的会话持久化与三种触发源入口本身属后续能力）；本次只要求"处理完成后会话被保存"这条契约成立。

### Key Entities *(include if feature involves data)*

- **会话（Session）**：一次对话的状态载体。关键属性：会话标识、所属 Agent 运行配置名、渠道、用户标识、对话历史、状态、创建/最后活跃时间。
- **对话历史条目**：会话里按序的一条往来记录，区分角色（用户消息 / 模型输出 / 工具结果）；模型输出条目可携带其提出的工具调用请求（调用标识、工具名、原始 JSON 参数）。
- **工具调用审计（`tool_invocations`）**：每次工具调用一条，成败均记。属性：所属会话、工具名、入参（JSON）、结果（JSON，失败时可为空）、成功标识、失败原因、耗时、链路标识、调用时间。
- **Agent 运行配置（Profile）**：复用第16节交付的载体；本次消费其身份提示、provider 选择、`max_iterations` / `max_history_turns` 与 `bootstrap` 字段。
- **线程级当前 Agent 上下文**：一次处理期间可见的"当前 Agent 运行配置"，不跨线程继承；处理出口必须清理。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 模型每轮都要求调用工具时，循环恰好执行声明的最大轮数次模型调用后强制收尾（一轮不多、一轮不少），并返回可识别的终止结果。
- **SC-002**: 一次包含 ≥2 轮工具调用的处理结束后，会话历史按序完整保留每一轮的模型输出与每一次工具结果，可逐条查回。
- **SC-003**: 会话历史超过声明上限时，进入模型的上下文只含最近 N 条对话消息（100% 不超限），且系统提示仍在。
- **SC-004**: 每一次工具调用（成功与失败）都能在审计里查到完整要素；失败记录 100% 带失败原因。
- **SC-005**: 处理过程抛异常的请求结束后，线程级上下文 100% 已清空（后续请求取不到上一个 Agent 的配置）。
- **SC-006**: 修改 Agent 定义正文 / 启动信息 / Skill 说明后，下一次组装立即反映新内容（无需重启、无缓存残留）。
- **SC-007**: 更换某 Agent 的模型或迭代上限只需修改该 Agent 自身的运行配置，循环代码零改动即可生效。

## Assumptions

- 依赖第16节已交付的模型调用统一入口（按会话标识 + Agent 运行配置发起一次调用、原样交回工具调用请求）、Agent 定义加载与内存索引、工具抽象（名称/描述/入参 schema/执行）与 `llm_calls` 审计栈。
- 循环自实现，不使用框架现成的 Agent/循环封装；执行权收敛在工具执行器一处。
- 长期记忆注入属后续能力（Memory）；本次只保留可选注入位，缺省跳过。
- 工具集合的来源（统一工具注册表）与其注册实现属后续 Tool 能力；本次以最小"按名解析工具"的契约定型，后续落地真实注册表。
- 会话持久化的真身（会话表 + 跨重启恢复）与三种触发源入口本身属后续 CLI/Web/定时能力；本次交付进程内会话存储与统一处理入口契约。
- 对外动作白名单（Sandbox）的具体规则属后续能力；本次仅保留"执行前校验"的调用位并标注接线处，不实现规则。
- 工具结果超长截断、工具 Policy（allow/deny）、工具并行调用、Agent 间委托、流式输出、上下文压缩均不在本次范围。
- 项目约定（AGENTS.md §6 /《技术方案》§11.1）：Skill 绑定用 Agent 目录内相对软连接表达、不写入运行配置 frontmatter。
- 目标平台为 JDK 21 + 虚拟线程；线程级上下文按"每请求独占一线程"的前提成立。
