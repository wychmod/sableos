# Feature Specification: 定时任务子系统与通知渠道注册表——让底座在无人值守时也持续正确

**Feature Branch**: `028-lesson28-scheduler-subsystem`

**Created**: 2026-10-31

**Status**: Draft

**Input**: User description: "第28节需求：定时任务子系统与通知渠道注册表——让底座在无人值守时也持续正确"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 定时任务可定义、能自己跑、跑完有账 (Priority: P1)

运营人员在一个 Agent 的运行声明里写一条定时配置（任务键、cron、时区、到点要发给 Agent 的消息）。进程启动后，这条任务自动登记进持久化存储，并算出下次触发时刻；到点系统自己把消息交给与 CLI / REST 完全相同的处理入口，跑完一次真实 ReAct，再把本次执行的成败、耗时、所用会话写进执行历史。任务列表里能看到下次触发时刻、上次结果与累计次数。

**Why this priority**: 这是本节存在的理由——没有持久化的任务状态与执行历史，定时任务只是"内存里一个会跑的 cron"，运营方无法回答"跑过几次、上次成没成、下次几点"，重启后也无从恢复。

**Independent Test**: 在 core 单测里用测试替身 store 驱动登记、启用检查、执行记录与失败隔离；整机 REST 验收由 US2 的 `ScheduledTaskE2ETest` 承载（它需要 US2 的管理端点）。

**Acceptance Scenarios**:

1. **Given** 工作区里有一个带定时配置的 Agent，**When** 启动整机，**Then** 任务列表里出现这条任务，含任务键、所属 Agent、cron、时区、启用状态、下次触发时刻，累计次数为 0。
2. **Given** 任务已登记，**When** 触发一次执行，**Then** 处理入口收到配置里的消息，任务累计次数加 1、上次结果与上次触发时刻更新、执行历史新增一条成功记录。
3. **Given** 任务已执行过，**When** 手动再执行一次，**Then** 累计次数继续增加，历史按开始时间倒序可查，会话仍是同一条定时会话。
4. **Given** 一次执行中途失败，**When** 查执行历史，**Then** 该条记录标记失败并带有人能读懂的原因；任务列表的上次结果同步为失败，调度器本身仍可继续触发下一次。

---

### User Story 2 - 定时任务可管理：立即执行与启用停用 (Priority: P1)

运营人员打开管理台的"定时任务"页，看到所有任务及其下次触发、上次结果、累计次数与启用状态；对某条任务点"立即执行"补跑一次，或点"停用"让它在下一个触发点被跳过；再点"启用"恢复。停用/启用不需要重启进程。

**Why this priority**: 定时任务要成为"可运营的一等公民"，光能跑不够，还要能看见、能补跑、能临时停掉。只读管理台在这里第一次出现写操作，这是"Agent OS 能执行智能定时任务"的落地界面。

**Independent Test**: 用 mock Agent 启动整机，通过 v2 端点查列表、立即执行、查历史、停用/启用；用 v1 端点验兼容与撞 key 409；`ScheduledTaskE2ETest` 承载该整机流程。

**Acceptance Scenarios**:

1. **Given** 任务处于启用状态，**When** 停用，**Then** 任务列表显示已停用；到点触发被跳过，不执行、不新增执行历史。
2. **Given** 任务处于停用状态，**When** 点"立即执行"，**Then** 仍执行一次并记历史（立即执行无视启用状态）。
3. **Given** 任务已停用，**When** 重新启用，**Then** 到点触发恢复正常。
4. **Given** 两个 Agent 声明了相同的任务键，**When** 通过旧版按任务键定位的接口执行/启停，**Then** 返回冲突而不是静默选择第一条。

---

### User Story 3 - 重启不失忆 (Priority: P2)

先跑几轮对话、攒几条长期记忆、让定时任务至少执行过一次，然后终止进程并重新启动。会话历史、长期记忆、定时任务的状态与执行历史、模型与工具审计记录全部原样可查；定时任务的定义从 Agent 声明重新登记，运行状态与历史从持久化存储恢复。

**Why this priority**: "状态全部放在进程外面"是底座走向分布式前必须成立的前提；只要有一项状态偷偷留在进程内存里，重启就会暴露。把这条做成可重复执行的验收，比翻日志可靠。

**Independent Test**: 在同一个临时工作区上先后启动两个应用实例（中间关闭第一个），第二个实例通过接口读回第一个实例写入的会话、记忆、任务状态与历史、审计记录。

**Acceptance Scenarios**:

1. **Given** 实例一已写入一条会话与一条长期记忆，**When** 关闭实例一、用同一工作区启动实例二，**Then** 通过接口能读回完整会话历史与记忆内容。
2. **Given** 实例一已执行过一次定时任务，**When** 启动实例二，**Then** 任务列表仍显示该任务、累计次数与上次结果，执行历史仍可查，下次触发时刻在未来。
3. **Given** 实例一已产生若干模型调用与工具调用审计，**When** 启动实例二，**Then** 审计记录连续可见，没有因重启丢失。

---

### User Story 4 - 多 Agent 并存不打架 (Priority: P2)

两个差异明显的 Agent 跑在同一实例上：A 只给文件工具，B 只给 HTTP 工具。交替使用时，A 的模型拿不到 B 独有的工具；A、B 的会话互不串；A 的定时任务失败不影响 B 的下一个触发点。

**Why this priority**: "OS"在核心阶段的最小体现就是多个 Agent 能在同一实例上同时用。三条隔离边界只要有一条失守，多 Agent 就只是"两个配置在同一个进程里互相踩"。

**Independent Test**: 用两个 mock Profile 启动整机，分别构建一次提示词并断言可用工具清单严格等于各自声明；分别取会话并断言标识不同；让 A 的定时任务失败后触发 B 的定时任务，断言 B 正常执行。

**Acceptance Scenarios**:

1. **Given** Agent A 只声明文件工具、Agent B 只声明 HTTP 工具，**When** 分别组装提示词，**Then** A 的可用工具清单不含 B 独有的工具，反之亦然。
2. **Given** A、B 各自发起对话，**When** 查会话列表，**Then** 两条会话的标识与归属 Agent 各自独立，不互相覆盖。
3. **Given** A 的定时任务执行失败，**When** B 的定时任务到达触发点，**Then** B 正常执行并记账，不被 A 的失败拖住。

---

### User Story 5 - 通知渠道可管理，notify 运行期解析 (Priority: P2)

运营人员通过 REST 登记一个 webhook 通知渠道（名称、类型、目标地址、可选描述），Agent 在正文里按渠道名引用。定时任务跑完后，`notify` 工具按渠道名从注册表解析目标并推送；改渠道地址立即生效，不需要改 Agent、不需要重启进程。渠道不存在或一个渠道都没登记时，工具明确报错且零请求发出。

**Why this priority**: 没有全局渠道注册表，定时链路的最后一步（把结果送出去）只能在日志里看到；第 19 节已把注册表后置，本节补齐后第 31 节两个 Demo 才有真实出口。

**Independent Test**: 通过 REST 新建一个指向本地 webhook 的渠道；让一个声明了 `notify` 工具的 Agent 执行一次；断言本地 webhook 收到内容、工具审计留一条成功记录。再把渠道地址改成白名单外域名并执行，断言工具审计留失败记录、调度器仍存活。

**Acceptance Scenarios**:

1. **Given** 注册表为空，**When** 调用 `notify`，**Then** 工具明确报错"无已注册的通知渠道"，零请求发出。
2. **Given** 已登记渠道 `team-webhook`，**When** Agent 按名调用 `notify`，**Then** 内容发往该渠道地址，`tool_invocations` 留一条成功记录。
3. **Given** 已登记多个渠道，**When** 调用 `notify` 时 channel 缺省/空白/为 `default`，**Then** 使用第一个登记的渠道。
4. **Given** 渠道地址指向白名单外域名，**When** 调用 `notify`，**Then** 沙箱拦下、`tool_invocations` 留一条失败记录、错误原因可读，调度器不被拖死。
5. **Given** 渠道地址被更新，**When** 下一次调用 `notify`，**Then** 使用新地址，不需要重启 Agent。

---

### Edge Cases

- 单条定时配置的 cron 或时区非法：只跳过该条并留下日志，不阻断其余任务注册与进程启动。
- 任务键为空、cron 为空、时区为空：视为非法配置，跳过并留下可定位日志。
- 两个 Agent 使用相同任务键：它们是两条独立任务，执行权、启停、历史互不相干；仅旧版按裸任务键定位的接口返回冲突。
- 配置里的任务键被改名或任务被删除：旧任务标记退役，不参与调度与活动列表，但状态与历史保留。
- 任务启用状态下到点触发时上一次仍未结束：本次跳过，不排队、不并发，不新增执行历史。
- 停用状态下到点：跳过、不执行、不记历史；立即执行仍可手动补跑。
- 执行历史里的错误信息：存人能读懂的原因（如"域名不在白名单内"），不存堆栈。
- 通知渠道名重复：新建返回冲突；更新/删除不存在的渠道返回未找到。
- 通知渠道类型：核心阶段只接受通用 webhook；其它类型返回参数错误。
- 定时任务状态与历史不得只存在进程内存里；进程中途退出不做补偿、不做自动重试。
- 外部 MCP server 连不上：记警告、跳过其工具，进程照常启动，不阻塞定时任务注册。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 定时任务的定义来源 MUST 保持唯一——只来自 Agent 运行声明里的定时配置；通过管理接口增删改 cron 定义不在本节范围。
- **FR-002**: 启动注册时，每条合法定时配置 MUST 登记到持久化任务表并取得稳定任务标识；同一 Agent 内同一任务键 MUST 复用同一标识，不得因重启生成新标识。登记内容含任务键、所属 Agent、展示名、cron、时区、消息与算出的下次触发时刻。
- **FR-003**: 单条定时配置非法（任务键 / cron / 时区缺失或解析失败）MUST 只跳过该条并留下日志，不阻断其余配置注册与进程启动。
- **FR-004**: 任务运行状态（启用与否、下次触发、上次触发、上次结果、累计次数、更新时间）MUST 持久化；每次**真正执行**无论成功失败 MUST 新增一条执行历史，含任务标识、定时会话标识、开始时间、成功与否、可读错误信息、耗时。
- **FR-005**: 任务处于停用状态时，到点触发 MUST 直接跳过、不执行、不新增执行历史；重新启用后恢复。
- **FR-006**: 管理面 MUST 能手动立即执行一次任务，不等 cron、无视启用状态；手动执行 MUST 与到点触发走完全相同的处理入口与会话身份，并同样写执行历史与更新任务状态。
- **FR-007**: 配置中删除任务或改变任务键后，旧任务 MUST 标记退役；退役任务不参与调度与活动列表，但其状态与历史 MUST 保留。
- **FR-008**: 系统 MUST 提供 v2 管理端点：任务列表、某任务的执行历史、立即执行、启用停用；另 MUST 提供按"Agent 名 + 任务键"精确定位的立即执行端点。管理台 MUST 只调用 v2。
- **FR-009**: 系统 MUST 保留旧版按任务键定位的 v1 管理路径作为兼容层；当多个 Agent 使用同一任务键时，v1 执行/启停 MUST 返回冲突，绝不静默选择第一条。
- **FR-010**: 会话、长期记忆、定时任务状态与执行历史、模型与工具审计 MUST 在进程重启后原样可查；定时任务定义 MUST 从 Agent 声明重新登记，状态与历史 MUST 从持久化存储恢复，不得以进程内状态为事实源。
- **FR-011**: 多个 Agent 并存时，工具清单 MUST 按各自声明过滤；会话标识 MUST 含 Agent 名且互不覆盖；一个 Agent 的定时任务失败 MUST NOT 影响其他 Agent 的下一次触发。
- **FR-012**: 通知渠道 MUST 以全局唯一名称登记，含类型、目标地址、可选描述与类型相关配置，并持久化；系统 MUST 提供列表、新建、更新、删除通知渠道的管理能力。
- **FR-013**: 通知渠道的创建 MUST 校验名称非空、类型为核心阶段支持的 webhook、目标地址非空；重名 MUST 返回冲突；更新/删除不存在的渠道 MUST 返回未找到。
- **FR-014**: `notify` 工具 MUST 在每次执行时从通知渠道注册表按名解析目标，不得缓存启动时的快照；channel 缺省、空白或字面量 `default` MUST 取第一个已登记渠道；渠道不存在或无渠道时 MUST 明确报错且零请求发出。
- **FR-015**: 通知发送前 MUST 经过既有的 HTTP 域名白名单校验；通知发送成败 MUST 走既有工具审计路径，不新增旁路。
- **FR-016**: 定时执行与通知推送 MUST 沿用既有超时兜底；执行历史中的错误信息 MUST 是可供人阅读的原因，不得写入堆栈。
- **FR-017**: 管理台 MUST 新增"定时任务"页，展示任务、所属 Agent、cron、下次触发、上次结果、累计次数、启用状态，并提供立即执行与启用/停用操作；该页只调用 v2 接口。
- **FR-018**: 旧版 v1 管理路径与新版 v2 管理路径 MUST 返回同一份任务状态与执行历史，不得出现两套账。

### Key Entities

- **定时任务**：一条 Agent 运行声明里的定时配置在运行态的代表；含全局稳定标识、所属 Agent、任务键（技术方案中的 `schedule_key`，Agent 内唯一）、展示名、cron、时区、消息、启用状态、退役标记、下次触发、上次触发、上次结果、累计次数、更新时间。展示名在核心阶段取任务键。
- **任务执行历史**：每次真正执行一条；含关联任务、定时会话标识、开始时间、成功与否、可读错误信息、耗时。成功与失败都记。
- **通知渠道**：全局唯一名称、类型（核心阶段 webhook）、目标地址、可选描述、类型相关配置、创建与更新时间；Agent 在正文中按名引用，不在运行声明里内联。
- **定时会话**：渠道与用户固定为调度标识、Agent 名为所属 Agent 的会话；与人推会话共用同一套会话存储与历史截断规则。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 一个只写了定时配置的 Agent，启动后任务列表里恰好出现一条已登记、启用、次数为 0 的任务，且下次触发时刻在未来。
- **SC-002**: 立即执行一次后，任务累计次数恰为 1、上次结果成功、执行历史恰有 1 条成功记录；定时会话只有 1 条，连续执行两次后仍只有 1 条且历史变长。
- **SC-003**: 停用后到点触发不执行、不新增历史；立即执行仍可补跑；重新启用后恢复。旧版按裸任务键定位、多个 Agent 撞键时返回冲突。
- **SC-004**: 同一工作区先后启动两个实例，第二个实例能读回第一个实例的会话、记忆、任务状态与历史、模型与工具审计，且数量与内容一致。
- **SC-005**: 两个 Profile 并存时，各自可用工具清单严格等于声明集合；会话标识互不相同；一个定时任务失败后另一个仍能执行。
- **SC-006**: 通知渠道 CRUD 可完成新建、列表、更新、删除；重名与不存在分别返回冲突与未找到。
- **SC-007**: 一次定时链路真实执行后，定时会话恰好 1 条、模型调用恰 2 条、工具调用恰 2 条（查询 + 通知）且全部成功，本地 webhook 恰收到一次消息。
- **SC-008**: 通知目标域名不在白名单时，工具调用留一条失败记录、错误原因可读，调度器仍能执行下一次任务。
- **SC-009**: 实现完成的定义是 `mvn clean verify` 全绿（含前端构建产物重建与本节门禁测试）。

## Assumptions

- 核心阶段为单实例部署，防重叠只需进程内互斥；分布式协调、选主、租约、自动重试与告警均归扩展阶段。
- 定时任务的 cron 定义仍随 Agent 文件与进程启动/重载生效，管理接口只管理运行状态与执行，不管理定义。
- 核心阶段通知渠道只支持通用 webhook；企业微信 / 飞书 / 钉钉专用 API 与邮件 SMTP 渠道归扩展阶段。
- 通知渠道先以 REST 管理，不单独做管理台页面；管理台的"定时任务"页只覆盖定时任务。
- 展示名在核心阶段没有独立的声明字段，取任务键作为展示名；不新增 Agent 运行声明字段。
- 定时任务与通知渠道的状态都放在进程外（SQLite + 文件系统），进程本身不保留事实状态。
- 旧版 v1 管理路径按任务键定位；多个 Agent 撞键时返回冲突，不做"默认第一条"的隐式选择。
- 外部 MCP server 不可用时只影响其工具，不阻塞进程启动与定时任务注册。
- 管理台页面渲染属人工验收项，门禁覆盖后端、接口契约与前端构建（类型检查 + 构建成功）。
