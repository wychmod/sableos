# Feature Specification: 插件化 Agent——一个目录定义一个会自己跑的 Agent

**Feature Branch**: `029-lesson29-pluggable-agent`

**Created**: 2026-10-31

**Status**: Draft

**Input**: User description: "第29节需求：插件化 Agent——一个目录定义一个会自己跑的 Agent"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 丢一个目录就多一个会自己跑的 Agent (Priority: P1)

业务方要新增一个每日订单对账 Agent。他只做一件事：在 Agent 目录根下建一个 `daily-reconcile/` 目录，里面写 `AGENT.md`——frontmatter 是这个 Agent 自己的运行配置（身份、用哪个模型、要用哪些系统能力、什么时候跑），正文是给模型的任务指令。系统启动时扫到这个目录，它出现在 Agent 列表里；到了它自己声明的时点，它自动跑完"想 → 调系统能力 → 答 → 推送"，审计留账。全程不写一行程序代码，不动一行底座。

**Why this priority**: 这是本节存在的理由，也是"能跑 Agent 的框架"与"能跑 N 个 Agent 的 OS"的分界线。没有这套"定义一个 Agent、装上去、让它跑起来"的标准机制，底座再完整也只是一个框架。

**Independent Test**: 在一个临时 Agent 根目录放 N 个 Agent 目录，扫描后注册表里正好出现 N 个 Agent（不多不少）；其中带定时声明的那些进入了调度器。全部用临时目录驱动，不依赖真实模型。

**Acceptance Scenarios**:

1. **Given** Agent 根目录下有一个合法 Agent 目录，**When** 执行启动扫描，**Then** 该 Agent 出现在已注册清单里，且其名称、模型、可用能力、定时声明与目录里的声明一致。
2. **Given** 根目录下放了 3 个 Agent 目录，**When** 执行启动扫描，**Then** 注册清单恰好 3 个，不产生任何别的条目。
3. **Given** 某个 Agent 目录的 frontmatter 声明了定时，**When** 完成注册，**Then** 该定时已交给调度器，且 cron 与时区取值来自该 Agent 自己的声明。
4. **Given** 某 Agent 的声明里引用了底座没有的系统能力，**When** 完成注册，**Then** 留下一条可定位的告警，但该 Agent 仍出现在清单里（不因一个未注册能力而丢弃整个 Agent）。

---

### User Story 2 - 非法 Agent 只废自己，不废整台机器 (Priority: P1)

运营半夜手工改了一个 Agent 的声明，把必填项写漏了或者 YAML 缩进弄坏了。第二天服务重启：这个坏 Agent 没有起来，日志里点名说清是哪个目录、缺了什么；其余 Agent 照常加载，进程正常启动，到点照常干活。

**Why this priority**: Agent 是业务方自己写的文件，写错是常态。若一个坏目录能拖垮整个进程，那"任意多个 Agent 并存"就不成立——这正是操作系统级机制与单程序配置的本质区别。

**Independent Test**: 在临时目录里混放合法与非法 Agent，扫描后合法者全部注册、非法者全部跳过且各自留下点名日志，扫描本身不抛异常。

**Acceptance Scenarios**:

1. **Given** 某 Agent 目录缺少主定义文件，**When** 扫描，**Then** 跳过该目录并留下点名日志，其余 Agent 正常注册。
2. **Given** 某 Agent 的 frontmatter 无法解析，**When** 扫描，**Then** 跳过该目录并留下点名日志，其余 Agent 正常注册。
3. **Given** 某 Agent 声明的名称与其所在目录名不一致，**When** 扫描，**Then** 跳过并点名不一致的双方，其余 Agent 正常注册。
4. **Given** 某 Agent 引用了未登记的模型提供方，**When** 扫描，**Then** 跳过并点名该提供方与 Agent，其余 Agent 正常注册。

---

### User Story 3 - 运行时新增的 Agent 立即可用 (Priority: P2)

不改配置文件、不重启进程，运行期新增一个 Agent：登记之后它立刻能被查到，它的定时立刻进入调度且留有可注销的句柄。下一节把这套能力包成接口、再加上文件监听，就能做到"上传即上线、丢目录即上线"。

**Why this priority**: 本节先把机制立好，下一节的接口上传与文件监听都建立在"运行时注册"这块地基上。没有它，新增 Agent 就必须重启。

**Independent Test**: 在运行中的注册表里登记一个 Agent，随即查询即可见；移除后再查即不可见；登记一个非法声明时，抛出的异常类型与消息和启动扫描路径完全一致。调度器登记单个 Agent 后，其每个定时都有可查询的句柄。

**Acceptance Scenarios**:

1. **Given** 一个正在运行的 Agent 注册表，**When** 登记一个新 Agent，**Then** 立即能按名查到它。
2. **Given** 注册表里有某 Agent，**When** 移除它，**Then** 按名查询不再命中，且移除操作返回"确实移除了"。
3. **Given** 一个非法声明，**When** 经运行时登记入口提交，**Then** 抛出的异常类型与消息，与启动扫描遇到同一非法声明时完全一致。
4. **Given** 调度器，**When** 登记一个带多条定时的 Agent，**Then** 每条定时都能查到对应句柄。
5. **Given** 同一 Agent 的同一任务被重复登记，**When** 第二次登记完成，**Then** 旧句柄被取消，不会出现同一任务两路同时触发。

---

### User Story 4 - 资源按需进上下文，不一次性全塞 (Priority: P2)

一个 Agent 目录里有四类东西：任务指令正文、参考资料、子指令规范、可执行脚本。触发时只有正文进入系统提示；参考资料与子指令要等模型觉得需要时，用底座的文件读取能力自己取；脚本要等要跑时，用底座的命令执行能力跑——只把脚本吐出的结果带进上下文，脚本代码本身不进。

**Why this priority**: 这是这套目录形态真正有价值的部分。全塞进去会挤占上下文、抬高成本、还让模型分心；按需取用让一个目录能装下远超上下文窗口的资料与能力。同时它也守住了底线：不新增工具、不建能力库、不建全局索引。

**Independent Test**: 组装一次系统提示，断言其中包含正文，但不包含参考资料、子指令、脚本的任何内容；改掉正文后再次组装，立即读到新内容。

**Acceptance Scenarios**:

1. **Given** 一个 Agent 目录，**When** 触发并组装系统提示，**Then** 提示里含任务指令正文，且不含参考资料与脚本的内容。
2. **Given** 同一目录，**When** 修改正文后再次组装，**Then** 读到的是新正文（不需要重启）。
3. **Given** 某 Agent 目录同时含正文与参考资料，**When** 统计进入系统提示的资料来源，**Then** 只有正文一类，参考资料仍留在目录中等待按需读取。
4. **Given** 一个 Agent 声明了脚本资源，**When** 触发，**Then** 脚本不被预先执行，也没有任何新的工具或索引被引入。

---

### Edge Cases

- Agent 根目录本身不存在或不可读：视为零个 Agent，正常启动，不留错误堆栈。
- Agent 根目录下存在普通文件（非目录）：忽略，不当作 Agent。
- 同一定时在同一 Agent 内被登记两次：后者的句柄取代前者，前者被取消，同一时点只跑一次。
- 一个 Agent 声明了多条定时：每条独立登记、独立记账，互不影响。
- 正文字段为空：不阻断注册，系统提示里该段整体省略。
- 运行时移除一个 Agent 后再登记同名 Agent：注册表以新声明为准、不残留旧条目；**调度句柄的清理不在本节范围**（`AgentScheduler` 只提供登记与查询，注销入口随第 30 节一并落地，见 `contracts/agent-scheduler.md`「不做的事」）。在此之前，同一 `(Agent, 任务)` 重新登记会复用 `scheduleId` 并取消旧句柄，但被删除的任务条目要到下次启动 `registerAll` 才退役。
- 脚本执行需要解释器，而解释器未被部署方加入白名单：命令被拒绝，失败原因进入工具审计，调度器本身不受影响。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 在启动时扫描 Agent 根目录，对其中每个子目录解析其主定义文件，拆出配置段（frontmatter）与正文（任务指令）两部分。
- **FR-002**: 系统 MUST 把配置段派生为底座认识的 Agent 运行配置对象，并登记进注册表——目录派生的 Agent 与手工定义的 Agent 使用同一个运行配置类型。
- **FR-003**: 目录派生的 Agent 与手工构造的运行配置 MUST 通过同一套校验（必填字段齐全、引用的模型提供方已登记），失败时抛出同一异常类型与同一消息。
- **FR-004**: 单个 Agent 目录非法（缺主定义文件、配置段无法解析、名称与目录名不一致、引用的提供方未登记）时，系统 MUST 只跳过该 Agent 并留下点名日志，不得阻断其余 Agent 加载与进程启动。
- **FR-005**: Agent 声明的系统能力清单里若含底座未注册的能力，系统 MUST 记录告警，但仍完成该 Agent 的登记。
- **FR-006**: Agent 的配置段里声明的定时 MUST 原样进入派生出的运行配置，并交给调度器注册；Agent MUST NOT 需要在任何其他位置重复声明定时。
- **FR-007**: 注册表 MUST 支持运行期登记、移除与存在性查询；启动扫描与运行期新增 MUST 走同一份注册表与同一套校验。
- **FR-008**: 调度器 MUST 提供按单个 Agent 登记其全部定时的入口，并 MUST 提供"某定时是否仍有登记句柄"的查询能力，供后续注销与更新使用。
- **FR-009**: 同一 Agent 的同一任务被重复登记时，系统 MUST 取消旧句柄，不得泄漏句柄，也不得让同一任务在运行时被触发两次。
- **FR-010**: Agent 正文 MUST 在被触发时进入系统提示（与启动信息同层），且 MUST 每次现读、不缓存，改动后下一次触发即生效。
- **FR-011**: Agent 目录中的参考资料、子指令与脚本 MUST NOT 被预加载进系统提示；它们 MUST 由正文指引用底座既有的文件读取与命令执行能力按需取用。
- **FR-012**: 本节 MUST NOT 为此新增任何对外工具、能力库或全局索引；Agent 目录本身 MUST NOT 被当作可执行工具。
- **FR-013**: 通知渠道 MUST NOT 出现在 Agent 配置段中；渠道由全局注册表管理，Agent 在正文中按名引用。
- **FR-014**: 系统 MUST 交付一个示例 Agent 目录，同时包含任务指令正文、可执行脚本、子指令规范与参考资料四部分，作为手动路径的参照物。
- **FR-015**: 脚本执行的信任边界 MUST 被明确记录：命令执行能力可调用部署方显式加入白名单的解释器，等价于授予模型当前系统用户的代码执行权限，不提供文件或网络隔离。

### Key Entities

- **Agent 目录**：一个自足的业务 Agent 的全部声明与资源，由主定义文件（配置段 + 正文）与可选参考资料、子指令目录、脚本目录构成；一个目录对应一个 Agent。
- **Agent 运行配置**：由配置段派生出的底座可用配置，含名称、身份、模型提供方与模型、可用系统能力清单、定时声明、启动信息、运行参数。
- **Agent 注册表**：运行期可按名查询的 Agent 集合，支持新增与移除；启动扫描与运行期新增共用。
- **定时句柄**：调度器为某条已登记的定时持有的可取消引用，用于重复登记时替换、以及后续注销。
- **示例 Agent**：一个四部分俱全的目录样例，覆盖正文常驻、脚本确定性取数、子指令按需读、参考资料兜底四种用法。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 往 Agent 根目录新增一个合法目录后，该 Agent 在已注册清单里出现，且其名称、模型、可用能力、定时声明与目录内声明逐项一致；全程无需编写任何程序代码。
- **SC-002**: 扫描含 3 个合法 Agent 的目录，注册结果恰好 3 个、无多余条目。
- **SC-003**: 混放合法与非法 Agent 时，合法者 100% 注册成功、非法者 100% 被跳过并各自留下点名日志，扫描过程不抛异常、进程正常启动。
- **SC-004**: 带定时声明的 Agent 全部进入调度器；每条定时的 cron 与时区与声明一致，且可查询到句柄。
- **SC-005**: 同一 Agent 的同一任务重复登记后，句柄数为 1，不会出现两路并发触发。
- **SC-006**: 系统提示中只含 Agent 正文，不含参考资料、子指令或脚本内容；修改正文后下一次组装即读到新内容。
- **SC-007**: 引用未注册能力的 Agent 仍被登记，同时产出恰好一条告警。
- **SC-008**: 运行时登记后按名查询立即可见；移除后立即不可见；非法声明经运行时入口与启动扫描抛出的异常类型与消息完全一致。
- **SC-009**: 实现完成的定义是 `mvn clean verify` 全绿，且本节全部验收用例在默认门禁内通过。

## Assumptions

- 核心阶段为单实例部署，重复登记的判据是进程内句柄；跨实例协调与选主归扩展阶段。
- Agent 目录位置固定为 Agent 根目录下的一级子目录，不支持多级嵌套。
- 同一声明中的名称必须与目录名一致；这条校验沿用既有加载器的口径，不另立规则。
- 通知渠道走全局注册表（已在第 28 节落地），Agent 只在正文中按名引用，配置段不含渠道字段。
- 示例 Agent 作为参照物交付，不默认写入运行期工作区，避免污染实际运行环境。
- 脚本执行不提供容器或网络隔离；不可信或多租户代码需等后续的隔离执行能力，在此之前只能在可信单机部署中开启解释器。
- Agent 版本管理、Agent 市场与共享、跨 Agent 能力复用、同名冲突策略、文件监听热加载均不在本节范围。
