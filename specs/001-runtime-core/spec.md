# 功能规格：SableOS 运行时内核（五大核心能力）

**功能分支**：`001-runtime-core`

**创建日期**：2026-10-05

**状态**：草稿

**输入**：SableOS 核心阶段的运行时内核——一套企业可自托管的 Java Agent OS 底座，让业务方不写 Java 代码，只靠 Agent 目录（AGENT.md + skills/ + scripts/）加 MCP server 就能跑起自己的 Agent，并通过 REST API 接入已有系统。五大核心能力按依赖顺序组织为 5 个用户故事。

## 用户场景与验收 *(必备)*

> 本规格的 P1–P5 表示**依赖顺序**（P1 最先具备，后续故事建立在前面的能力之上），**不代表重要性**。用户故事 5 因依赖前四项能力就绪而排在最后，其重要性很高。

### 用户故事 1 - 对接模型提供方（优先级：P1）

业务方在同一实例里配置多个模型提供方（核心阶段至少覆盖两家，例如 DeepSeek 与 Kimi），在 Agent 配置里指定用哪一个；换模型不需要改代码，也不被某一家供应商锁定。

**为什么是这个优先级**：这是所有后续能力的前置——没有模型调用就没有 ReAct、Memory 与 Tool。且"不锁定单一供应商"是产品定位里"企业可掌控"的第一条具体体现。

**独立验证方式**：配置两个模型提供方，用同一段提示分别调用，两者都能返回结果；把某个 Agent 的提供方配置从 A 改成 B，行为随之改变且无需改代码。

**验收场景**：

1. **给定**一个 Agent 已配置模型提供方，**当**用户发起一次对话，**则**得到该提供方的模型响应并正常结束本轮。
2. **给定**同一实例配置了两个不同的模型提供方，**当**分别用它们运行同一任务，**则**两次都成功且互不干扰。
3. **给定**Agent 指定的模型提供方未在实例配置中注册，**当**该 Agent 被加载或首次调用，**则**系统明确报错指出未注册的提供方，而不是静默回退到别的提供方。

---

### 用户故事 2 - ReAct 循环：Agent 自主多步完成任务（优先级：P2）

用户给一个需要多步操作的任务（例如"查明天天气并给穿搭建议"），Agent 自己决定调用工具、读取结果、再继续思考，直到给出最终回答；如果任务无法在限定轮次内完成，循环会强制结束而不是无限打转。

**为什么是这个优先级**：这是"Agent 大脑"，把模型从单轮问答变成能自主干活的执行体；用户故事 3、4 的能力都通过这个循环被使用。

**独立验证方式**：用一个至少需要两轮工具调用的任务观察循环轮次、工具调用与最终回答；再用一个必然无法收敛的任务验证达到上限后正确终止。

**验收场景**：

1. **给定**一个需要多次工具调用的任务，**当**任务运行，**则**每一轮的模型输出与工具结果都被累积进该会话的对话历史，最终产出完整回答。
2. **给定**一个在限定轮次内无法完成的任务，**当**达到迭代上限，**则**循环被强制结束并返回可解释的终止原因（不是静默截断）。
3. **给定**工作区里存在一个目录形式的 Agent 定义，**当**用户与它对话，**则**它的运行配置（身份、提供方与模型、可用工具、迭代上限等）取自该目录的配置文件，正文任务指令被注入到提示词中。
4. **给定**同一实例中并存多个 Agent，**当**分别与它们对话，**则**各自的配置与历史互不串扰。

---

### 用户故事 3 - Memory：跨对话记住用户与项目（优先级：P3）

用户在与 Agent 的对话里说"以后更关注 AI 和芯片"，之后再开新对话时，Agent 的产出已经体现了这个偏好，用户不需要重复交代；长期记忆以用户可读、可手工编辑的文件形式存在。

**为什么是这个优先级**：让 Agent 从"每次都从零开始"变成"越用越懂你"，是 Agent OS 相对一次性脚本的核心价值；同时它是用户故事 4 里记忆类工具的宿主能力。

**独立验证方式**：对话中让 Agent 记住一个偏好，新开会话后询问相关话题，回答体现该偏好；再手工编辑记忆文件，观察下一次组装上下文时变更立即生效。

**验收场景**：

1. **给定**一个全新工作区，**当**用户要求 Agent 记住某个偏好，**则**该偏好被写入长期记忆并可在文件中看到。
2. **给定**长期记忆里已有某偏好，**当**用户在新会话里提问相关话题，**则**回答体现该偏好，无需用户重复说明。
3. **给定**长期记忆文件被人工编辑或删除，**当**Agent 下次组装上下文，**则**变更立即生效（系统不缓存旧内容）。
4. **给定**一次长对话，**当**会话历史超出配置的保留范围，**则**超出部分按配置截断，而核心记忆区永不被截断。

---

### 用户故事 4 - Tool 体系：内置工具 + 零代码扩展 + 沙箱约束（优先级：P4）

业务方想让 Agent 会干更多事，最省事的方式是只写配置文件（Agent 目录里的技能 + 外部 MCP server 声明）而不写任何代码；同时所有文件读写、网络访问、命令执行都受白名单约束，越权操作被拒绝且留有记录。

**为什么是这个优先级**：这是"能干事"的能力，也是产品差异化的关键——三档扩展方式决定了业务方的接入成本。沙箱约束与审计同属企业可信任的前提。

**独立验证方式**：只写配置（不写代码）接入一个外部 MCP server，让 Agent 调用它；再尝试访问白名单外的路径、域名与命令，验证被拒绝且拒绝原因可读。

**验收场景**：

1. **给定**工作区声明了一个外部 MCP server，**当**Agent 需要它提供的能力，**则**调用成功且结果进入对话历史。
2. **给定**一个 Agent 目录里绑定了技能，**当**该 Agent 组装提示词，**则**提示词中只出现技能元数据，技能正文由模型按需读取；业务方全程未写代码。
3. **给定**一次对白名单外路径、域名或命令的访问尝试，**当**该次工具调用发生，**则**调用被拒绝、原因对用户可读，且这次调用仍留下可查记录。
4. **给定**一次成功的工具调用，**当**事后审计，**则**该调用的输入、结果与耗时都能被查询到。
5. **给定**一次模型调用，**当**事后审计，**则**该次调用的模型、用量与耗时都能被查询到。

---

### 用户故事 5 - Web Service 与三种触发入口收口（优先级：P5）

外部系统通过 HTTP/JSON 接口调用 SableOS：创建会话、调用 Agent、查询会话与配置信息；同一个 Agent 既可由命令行触发、也可由外部系统调用、还可按计划自动运行，三条入口走同一条处理链路；会话记录跨进程重启仍在。

**为什么是这个优先级**：这是 SableOS 区别于个人助手项目的关键能力（对外集成），但依赖前四项能力全部就绪，故排在最后。

**独立验证方式**：启动服务后，用 HTTP 客户端完成"创建会话 → 调用 Agent → 查询该会话完整记录"的闭环；重启进程后仍能查到该会话；配置一个定时触发的 Agent，等它到点自动运行并在会话记录中看到结果。

**验收场景**：

1. **给定**服务已启动，**当**外部系统创建会话并调用 Agent，**则**得到处理结果，且该会话的历史记录可被查询。
2. **给定**同一 Agent 配置了计划触发，**当**到达设定时间，**则**它无需人工干预自动运行，且运行过程可作为会话查询到。
3. **给定**自动触发过的 Agent，**当**用户手动补跑一次，**则**走的是同一条处理链路，结果同样可查。
4. **给定**进程重启，**当**查询此前创建的会话，**则**历史完整可读。
5. **给定**同一实例配置了多个 Agent，**当**分别通过不同入口调用它们，**则**各自独立可用、互不干扰。
6. **给定**一个全新环境，**当**用户执行工作区初始化，**则**得到可直接使用的目录结构与配置骨架，并至少有一个示例 Agent 可跑通。

### 边界情况

- 模型提供方认证失败、网络超时或返回不可解析的工具调用格式时，循环如何终止、用户看到什么？
- 单次工具返回内容超大（例如整篇网页）时，如何避免撑爆上下文？
- 达到迭代上限时仍未得出结论，返回什么给用户？是否保留已完成的中间步骤？
- 长期记忆文件被外部删除、损坏或包含非法结构时，启动与运行分别如何降级？
- 白名单未配置任何条目时的默认行为是什么？（默认拒绝，最小权限）
- 计划触发到点时进程未运行，错过的触发是否补跑？
- 并发对同一会话发起调用时，会话历史如何保持一致？
- 工具调用本身超时或抛异常时，循环是继续还是终止？

## 需求 *(必备)*

### 功能需求

#### 模型提供方（核心能力一）

- **FR-001**：系统必须支持在同一实例中并存多个模型提供方，并由 Agent 的配置指定使用哪一个。
- **FR-002**：系统必须在运行时不修改代码即可切换 Agent 使用的提供方或模型。
- **FR-003**：系统必须维护"提供方名称 → 具体模型客户端"的显式映射，未注册的名称必须导致明确失败，禁止通过自动扫描隐式发现。
- **FR-004**：系统必须在核心阶段至少跑通两个不同提供方的完整对话链路。
- **FR-005**：系统必须在模型调用失败（认证失败、超时、返回格式异常）时给出可定位的失败原因，而不是静默重试或静默回退到其他提供方。

#### ReAct 循环（核心能力二）

- **FR-006**：系统必须让 Agent 自主完成"思考 → 调用工具 → 读取结果 → 继续"的多轮循环，直至产出最终回答。
- **FR-007**：系统必须将每一轮的模型输出与工具结果按顺序累积到该会话的对话历史中。
- **FR-008**：系统必须提供可配置的迭代上限，达到上限时强制终止循环并返回可解释的终止信息。
- **FR-009**：系统必须自行实现上述循环控制，不得依赖外部框架的自动工具执行机制（工具的选择与执行时机完全由本系统的循环控制）。
- **FR-010**：系统必须以"一个目录 = 一个 Agent"的方式加载 Agent 定义：目录配置文件承担运行配置，正文承担任务指令。
- **FR-011**：系统必须支持同一实例内多个 Agent 并存，各自的配置、会话与工具集互不串扰。

#### Memory（核心能力三）

- **FR-012**：系统必须提供会话记忆（当前对话上下文）与长期记忆（跨对话保留）的统一读写入口。
- **FR-013**：系统必须提供让 Agent 显式写入长期记忆的能力，写入内容对用户可见、可手工编辑。
- **FR-014**：系统必须提供按关键词检索长期记忆的能力。
- **FR-015**：系统必须在每次组装上下文时读取长期记忆的最新内容，不得缓存过期版本。
- **FR-016**：系统必须在会话历史超出配置保留范围时按配置截断，且长期记忆的核心区永不被截断。
- **FR-017**：长期记忆必须划分为核心区与归档区，写入哪个区由调用方显式指定，系统不得自行猜测。

#### Tool 体系（核心能力四）

- **FR-018**：系统必须提供内置工具集，至少覆盖：文件读取、文件写入、目录列举、HTTP 请求、受限命令执行、记忆写入、记忆检索、消息通知。
- **FR-019**：系统必须支持三档工具扩展方式：仅写配置（Agent 目录技能 + 外部 MCP server）、轻量代码（独立 MCP server）、注解式代码。
- **FR-020**：仅写配置的扩展方式必须无需编写任何代码即可让 Agent 获得新能力。
- **FR-021**：系统必须在提示词中只注入技能的元数据（名称与描述），技能正文由模型按需读取。
- **FR-022**：所有工具执行必须经过沙箱约束：文件路径、网络域名、可执行命令均按白名单校验，未命中白名单的操作必须被拒绝。
- **FR-023**：系统必须不依赖进程级安全管理器实现沙箱（该机制在当前运行平台上已不可用），沙箱约束必须在应用层实现。
- **FR-024**：系统必须记录每一次工具调用（调用方、工具名、入参、结果、耗时、成功与否），并使其可被查询。
- **FR-025**：系统必须记录每一次模型调用（提供方、模型、用量、耗时、成功与否），并使其可被查询。
- **FR-026**：审计记录必须在核心阶段即真实落库，而不是仅写日志文件等待后期反解析。

#### 对外接口、触发链路与工程化（核心能力五）

- **FR-027**：系统必须提供 HTTP/JSON 接口，至少覆盖：会话管理、Agent 调用、配置与记忆与工具信息查询、健康与运行信息查询，合计不少于 10 个端点。
- **FR-028**：系统必须提供命令行入口，覆盖工作区初始化、对话、服务启动、配置与 Agent 管理等日常操作。
- **FR-029**：系统必须支持三种触发入口——命令行、外部接口调用、计划自动运行——且三者复用同一条 Agent 处理链路。
- **FR-030**：系统必须支持按计划（定时）自动触发 Agent，且触发记录可作为会话查询。
- **FR-031**：系统必须支持对计划任务的手动补跑，且补跑与自动触发走同一条链路。
- **FR-032**：系统必须将会话、审计记录与任务状态持久化，保证进程重启后可恢复查询。
- **FR-033**：系统必须提供工作区初始化能力，生成可用的目录结构与配置骨架。
- **FR-034**：系统必须支持从环境变量加载密钥，且不得将密钥写入对话内容或日志。
- **FR-035**：系统必须支持将消息通知发送到外部渠道，渠道以全局注册名引用，新增或修改渠道不需要改动 Agent 定义。
- **FR-036**：通知的渠道配置必须由统一注册表管理，Agent 定义中不出现具体渠道地址。
- **FR-037**：系统必须提供结构化日志，使运行过程可观测、问题可定位。
- **FR-038**：系统必须提供对外的项目主页入口，说明产品定位与快速开始方式。

### 关键实体（涉及数据时必填）

- **Agent 定义**：一个目录，包含运行配置（身份、提供方与模型、可用工具、迭代上限、会话保留范围、计划触发、渠道）、任务指令正文，以及可选的技能绑定与脚本。
- **运行配置快照**：由 Agent 定义派生出的运行时配置，按名称被索引，是触发入口查找 Agent 的依据。
- **会话**：一次连续交互的载体，包含标识（渠道 + 用户 + Agent 联合确定）、消息历史、状态；计划触发同样落在会话中。
- **消息**：会话内的一条记录，区分角色（系统指令、用户、模型、工具结果）与时间顺序。
- **长期记忆条目**：跨会话保留的事实或偏好，分核心区与归档区，以用户可读文件形态存在。
- **工具调用记录**：一次工具执行的完整留痕（工具名、入参、结果、耗时、结果状态）。
- **模型调用记录**：一次模型调用的完整留痕（提供方、模型、用量、耗时、结果状态）。
- **技能**：可复用的能力包，以元数据（名称、描述）对外暴露、正文按需读取；Agent 通过目录内的绑定关系决定可见范围。
- **通知渠道**：全局注册的外部消息出口，含名称、类型、地址与可选描述。
- **计划任务**：绑定到某个 Agent 的时间触发定义，含状态与执行历史。

## 成功标准 *(必备)*

### 可衡量的结果

- **SC-001**：两个端到端场景（每日天气、每日科技日报）可以完整跑通，且都为"到点自动运行 + 可手动补跑"，这是核心阶段发布的硬条件。
- **SC-002**：业务方在"每日科技日报"场景中全程不写任何代码，仅通过配置文件即让 Agent 完成汇总与推送。
- **SC-003**：新用户可在 30 分钟内完成单节点部署并跑通首个 Agent。
- **SC-004**：单节点可稳定运行 10 个 Agent 连续 4 小时，无中断、无串扰。
- **SC-005**：单节点支持 100 个并发会话。
- **SC-006**：会话创建请求的 P99 响应时间低于 200ms；入口转发到内部处理的额外开销低于 50ms。
- **SC-007**：每一次工具调用与模型调用都可在事后被检索到（覆盖率 100%），包括被沙箱拒绝的调用。
- **SC-008**：进程重启后，此前创建的会话与记录 100% 可查询。
- **SC-009**：达到迭代上限或工具连续失败时，100% 正确终止并给出可解释原因，不出现死循环或同一工具被重复执行。
- **SC-010**：同一实例并存的多个 Agent，其配置与会话零串扰。
- **SC-011**：运维方可在不修改源码的前提下，依据运行日志定位一次失败的调用（含失败的模型调用与工具调用）。
- **SC-012**：项目主页可被外部访问，且能让新读者在 5 分钟内说清 SableOS 是什么、五大能力是什么、如何快速开始。

## 假设与前提

- **部署形态**：企业自托管的单节点实例，运维方可直接访问工作区所在文件系统；不涉及分布式部署与多副本共享。
- **目标角色**：业务方（编写 Agent 定义与配置，不需写代码）、运维方（部署、配置密钥与白名单）、外部系统（通过 HTTP 接口集成）。
- **范围边界**：本功能只覆盖五大核心能力的运行时内核。多租户、单点登录、完整审计查询界面、工具治理属扩展阶段，只预留扩展点；技术方案中带编号的后续增量（知识库、人格库、飞书/企微/钉钉等入站渠道、记忆多后端升级）属后续功能，不在本规格范围。
- **接口安全**：核心阶段不做用户级鉴权与多租户隔离，假设部署在受信网络内；但密钥必须不落日志与对话。
- **长期记忆**：核心阶段不自动从对话中抽取记忆，写入时机由 Agent 显式决定；核心区/归档区的划分由调用方指定。
- **任务收敛**：迭代上限有默认值并可配置；未配置时使用默认值。
- **计划触发**：依赖进程常驻，进程未运行期间错过的触发不自动补跑，用户可通过手动补跑补上。
- **审计记录**：核心阶段只写入与查询审计记录，不提供治理级的审计分析与报表（属扩展阶段）。
- **技术约束**：具体技术栈与架构约束由项目宪章与《技术方案》决定，本规格只描述行为与结果，不重复技术选型。
- **验收依据**：验收标准复用《需求文档》第 13 章的功能验收清单、两个端到端 Demo，以及同章的性能验收与可运维性验收条目。
