# Phase 0 研究：SableOS 运行时内核

**目的**：把技术上下文里的未知项与待定项收敛成可执行决策。凡《技术方案》已给出结论的，直接引用不再重新论证；只对**文档之间冲突**或**文档未覆盖**的点给出决策与待确认标记。

## D-01 ReAct 循环实现方式

- **决策**：自实现循环（组装 Prompt → 调 LLM → 有工具调用则执行并回填 → 继续；达到上限强制终止），不依赖任何框架的 Agent 抽象。
- **理由**：宪章原则 II；循环是核心可审计点。
- **备选**：Spring AI 的 Agent/工具自动执行链 —— 被否决，会导致同一工具被调用两次且审计链路断裂（技术方案决策二）。

## D-02 Spring AI 使用边界

- **决策**：只用两件事——`ChatClient` 的调用与协议转换、`@Tool` 注解的 JSON Schema 生成；工具调度与执行完全由 `ReActLoop` + `ToolExecutor` 负责。
- **理由**：技术方案决策二；宪章原则 III。
- **落地约束**：禁止注册框架自带的工具执行回调；任何"让框架自己执行工具"的配置都属于违规。

## D-03 Provider 解析方式

- **决策**：`ProviderService` 启动时按配置中声明的 provider name 建立**显式映射表**（provider name → `ChatModel`）。
- **理由**：容器内多个同类型 `ChatModel` Bean 无法靠类型可靠区分；宪章原则 IV。
- **备选**：类型扫描自动发现 —— 否决；`@Qualifier` 是可选实现手段，但"显式映射"这一原则不可退让。

## D-04 长期记忆后端范围（已定）

- **决策**：本次交付 `LongTermMemoryStore` 后端接口 + **两个零外部依赖的实现**：`MarkdownMemoryStore`（默认档，`.sableos/memory/MEMORY.md`，核心区/归档区两个分区，不缓存、核心区永不截断）与 `SqliteMemoryStore`（`memory_entries` 表，`scope` 列承载同一套分区语义，按 `memory.backend` 配置切换）。**Mem0 档与语义检索升级（015）不在本次范围**。
- **理由**：技术方案第 5.1 节要求核心阶段"三档一次交付"，其真实意图是**接口墙一次立起、上层不感知后端差异**——这一点本次完整满足（换后端只改一行配置，`MemoryService` 以上不动）。两档内置后端零外部依赖，且 SQLite 档顺带把 `memory_entries` 表在本次建好，避开技术方案第 9.2 节警告的 SQLite 迁移成本。
- **Mem0 为何后置**：它需要业务方自托管一个外部 Mem0 服务，凭证与地址走环境变量；离线与 CI 环境无法验收，属"外部集成档"。接口已就位，后续新增一个实现类即可。
- **备选**：三档齐交付（否决：为无法离线验收的外部集成付出本次的交付风险）；只交付接口 + Markdown 档（否决：SQLite 档零新增依赖，晚建表要付迁移成本）。

## D-05 存储与表结构演进

- **决策**：SQLite + Spring Data JPA；表结构由 **Flyway 双轨目录** `db/migration/{vendor}/` 管理（SQLite 为默认零配置档，PostgreSQL 作为部署选项按 URL 自动识别）。
- **理由**：技术方案决策七及第 9.2 节的工程风险提示（SQLite 的 `ALTER TABLE` 能力弱，不能依赖 `hibernate.ddl-auto=update` 做表结构演进）。
- **落地约束**：首次建表也走迁移脚本，不依赖自动建表。

## D-06 会话身份生成规则

- **决策**：`session_id = f(channel, user, profile)`；各渠道的用户标识来源按 spec 澄清记录第 2 条——CLI 取本机用户名、计划触发固定 `scheduler`、HTTP 由请求参数提供且缺省 `anonymous`。
- **理由**：技术方案 8.5/9.2 已给出公式与钟推口径，本计划只补 HTTP 与 CLI 侧来源，避免"忘了传就静默合并"的歧义。
- **备选**：服务端固定单用户（否决，会让 `user_id` 变成死数据）；HTTP 强制必传（否决，抬高首次调用门槛且与 SC-003 冲突）。

## D-07 定时触发的范围

- **决策**：`AgentScheduler` 基于 `ThreadPoolTaskScheduler` + `CronTrigger` 动态注册；任务定义只来自 `AGENT.md` frontmatter 的 `schedules`；单任务用进程内 `ReentrantLock` 防重叠（上一次未跑完则跳过，不排队）；执行失败只记日志且仍走完整审计路径；**不落任务状态表、不提供 v2 管理端点**。
- **理由**：spec 澄清记录第 1 条（项目方选定最小形态）；符合宪章原则 VIII。
- **备选**：完整形态（两张任务表 + `/api/v2/schedules` + 启停）—— 被项目方在澄清阶段否决。

## D-08 沙箱与白名单

- **决策**：`Sandbox.enforce(SandboxAction)` 单一入口，`ActionType` 取文件读/文件写/Shell 命令/HTTP 请求四值；核心阶段唯一实现 `WhitelistSandbox`，按类型路由到路径、命令、域名（以及 SMTP 端点，为后续 email 渠道预留）四个校验分支；校验失败抛异常，走 `ToolExecutor` 既有的失败审计路径。
- **默认策略**：白名单未配置时**默认拒绝**；工作区初始化生成带注释的最小白名单（spec 澄清记录第 3 条）。
- **理由**：宪章原则 VII；技术方案决策六。
- **风险知情**：应用层白名单是"劝阻级"防线，防模型误操作，不防蓄意绕过；核心阶段不用于运行不可信代码。

## D-09 工具结果与循环终止策略

- **决策**：单次工具结果超过可配置阈值时按字符数截断并标注「已截断 + 原始长度」，循环继续（spec 澄清记录第 4 条）；达到迭代上限时返回最后一条模型输出 + 明确终止原因，保留全部中间步骤（spec 澄清记录第 5 条）。
- **理由**：两者都要求"行为确定且可断言"，避免失败路径上出现无法测试的模糊行为。
- **备选**：落盘 + 摘要（引入文件生命周期，留扩展）；追加"总结请求"再终止（多一次调用且仍可能不收敛）。

## D-10 上下文长度管理

- **决策**：默认保留最近 `max_history_turns` 轮（技术方案 4.3 给出默认 20 轮），超出丢弃；核心区长期记忆永不截断；不缓存长期记忆文件（每轮重读）。
- **理由**：技术方案 4.3/5.3 已有结论；不做总结压缩（扩展阶段）。

## D-11 审计写入范围

- **决策**：本次只写不查——`tool_invocations` 与 `llm_calls` 在每次调用后落库（含被沙箱拒绝的调用、含定时触发的失败调用）；查询接口与报表留扩展阶段。
- **理由**：宪章原则 VI；技术方案第 9.2 节的调整说明。

## D-12 通知出站

- **决策**：`NotifyChannelAdapter.send(NotifyTarget, content)` 接口先行，核心阶段只实现 `WebhookNotifyAdapter`；渠道由 SQLite 全局注册表管理（`notify_channels` 表），Agent 正文按名引用；发送前复用同一份 HTTP 域名白名单。
- **理由**：技术方案 6.8；与入站 `ChannelAdapter` 分开建模（方向相反）。
- **注**：`notify_channels` 表的管理端点（CRUD）按技术方案属扩展阶段——本次**不提供 CRUD 端点**，但必须提供一条可用的登记途径：定义源为工作区文件 `.sableos/notify_channels.yaml`（与 `mcp_servers.yaml` 同形态，`init` 生成模板），启动时 reconcile 进表。否则 Demo 一/二的推送目标无从配置（详见 `plan.md` 的范围偏差表）。

## D-13 测试策略

- **决策**：JUnit 5 + Spring Boot Test；核心链路（ReAct 循环、ToolExecutor 审计、Sandbox 拒绝路径、会话持久化、Provider 显式映射）必须有测试覆盖；端到端验收按 `quickstart.md` 的场景执行。
- **理由**：《需求文档》第 13 章要求"每个功能模块至少有一个端到端测试用例覆盖"；技术方案未细化，按此默认执行。
- **注**：宪章未强制测试先行（TDD 条款在定稿时被明确排除），因此计划不设置"测试先写"的门槛，但要求每条 FR 有可断言的验证点。
