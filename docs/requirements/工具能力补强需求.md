# 工具能力补强需求：四个内置工具的迭代

**状态**：需求池（待排期）｜ **涉及模块**：`sableos-tool`（`builtin/`）、`sableos-boot` 装配 ｜ **对应课件**：第 20 节 §6「把基础工具补齐到业界水准」

> 这份文档不是 Spec-Kit 的 feature 产物，而是**一份需求**：讲清"为什么要做、做成什么样、怎么验收"。进入实施时按 `docs/class/Spec-Kit 执行指导` 开 feature，本文直接作为 `specify` 的输入；四件可按优先级拆成四个 feature，也可两两合并。

---

## 一、要做什么

第 20 节交付的 12 个内置工具覆盖了"读写文件、跑命令、调 API、记事、往外推"的最短闭环，Agent 已经"能动手"。但要让它**长时间独立干活**，对照 Claude Code / Codex CLI / Cline / OpenHands 的公约数，还缺四样高频能力：

| # | 迭代项 | 现状的疼点 | 目标 | 优先级 |
|---|--------|------------|------|--------|
| 1 | **read_file 分页 + 行号** | 整文件 `readString`，3000 行文档直接吃掉大半 context；返回无行号，模型无法按行定位 | 按 `offset/limit` 读，默认 2000 行，带稳定行号与截断提示 | P0 |
| 2 | **multi_edit 批量编辑** | 一次只能改一处，改 5 处要 5 轮；中途失败文件处于"改了一半" | 一次调用多处精确替换，**全成功才落盘** | P0 |
| 3 | **web_fetch 网页正文** | 只有 `http_get` 返回原始 HTML，噪声极大；`web_search` 只给摘要 | URL → 正文 Markdown/纯文本，带类型判断、大小上限、重定向复查 | P1 |
| 4 | **todo_write 任务清单** | 长任务没有外部化进度，模型容易跑偏、重复劳动 | 维护一份结构化任务清单，模型每步更新 | P1 |

**为什么是这四件**：它们是"agent 独立完成一个多步任务"的最小补齐——读得动大文件（1）、改得动多处代码（2）、拿得到网页正文（3）、记得住自己要干什么（4）。其余能力（浏览器自动化、视觉、子 agent、代码解释器）依赖重、边界复杂，统一走 MCP 生态，不进内置工具面。

**明确不做**：`apply_patch`。上下文模糊匹配会绕开现有"唯一匹配"的安全保证，改错位置难以追溯，与项目"改动可审计"的定位冲突；跨文件大重构交给 MCP 侧工具或未来子 agent。

## 二、四条共同约束（四件都适用）

1. **不新增工具抽象**：全部复用 `SableTool` + `@Tool` 注解管道 + `ToolRegistry`，不引入第二种注册方式。
2. **Sandbox 永远第一行**：任何涉外动作（文件读写、HTTP）执行前先 `sandbox.enforce(...)`，不过则异常拦下、动作零发生。新增 `web_fetch` 必须对**每一次重定向后的最终 URL** 再校验一次——这是 SSRF 的关键防线。
3. **审计不建旁路**：成败与耗时统一由 `ToolExecutor` 落 `tool_invocations`，工具内部不写库、不写日志替代审计。
4. **契约自动纳入**：`SableToolContractTest` 参数化遍历注册表，新工具自动被检查 name/description/inputSchema 三件套非空——任何一件漏 schema 立刻红。

## 三、迭代 1：read_file 分页与行号（P0）

### 3.1 接口

```java
@Tool(name = "read_file", description = "读取文本文件的指定行范围，返回带行号的内容")
public String readFile(
    @ToolParam(description = "文件路径") String path,
    @ToolParam(required = false, description = "起始行号，从 1 开始，默认 1") Integer offset,
    @ToolParam(required = false, description = "最多读取行数，默认 2000，上限 2000") Integer limit)
```

### 3.2 行为规格

| 输入/场景 | 输出 |
|-----------|------|
| 正常范围 | 每行 `%6d\t%s`（行号右对齐 6 位 + TAB + 原文） |
| 未读到文件末尾 | 末尾追加 `…（共 N 行，已显示 a–b；用 offset=b+1 继续）` |
| 读到末页 | 不追加提示 |
| `offset < 1` / `limit < 1` | 参数错误，失败结果点名（不抛裸异常给模型） |
| `limit > 2000` | 夹到 2000，提示里说明"上限 2000" |
| `offset > 总行数` | `（文件共 N 行，起始行 M 超出范围）`，不抛异常 |
| 空文件 | `（空文件）` |
| 文件不存在 / 非普通文件 | `IllegalArgumentException`，消息含路径 |

**设计取舍**：行号用 TAB 而非 `:` 分隔——内容本身可能含冒号（`grep` 已踩过）；行号是给模型定位与讨论用的，`edit_file` 仍按字符串匹配，不依赖行号，因此两边不会耦合。

**兼容性**：返回格式变化属于行为变更，`FileToolsTest` 中断言全文相等的用例需同步修改；工具名与参数名不变，schema 层兼容（新增两个可选参数）。

## 四、迭代 2：multi_edit 批量编辑（P0）

### 4.1 接口

```java
@Tool(name = "multi_edit", description = "在一个文件内按顺序应用多处精确替换，全部成功才写入")
public String multiEdit(
    @ToolParam(description = "文件路径") String path,
    @ToolParam(description = "编辑列表，按顺序应用") List<Edit> edits)

public record Edit(
    String oldString,
    String newString,
    Boolean replaceAll) {}
```

### 4.2 行为规格

1. **顺序语义**：后一个 edit 作用于前一个 edit 改完的文本（允许"先插入、再改插入内容"）。
2. **原子性（最重要）**：全部 edit 在内存中依次应用，**任一失败 → 整体失败、文件字节不变**；全部成功后才一次 `Files.writeString`。
3. **唯一性**：默认要求 `oldString` 唯一出现；`replaceAll=true` 时替换全部并返回替换次数。多处匹配且未开 `replaceAll` → 失败，点名第几个 edit、第几次出现。
4. **错误语义**：失败消息必须包含「第 N 个 edit + 原因（未找到 / 多处匹配 / 空 oldString）」，方便模型自我修正后重试。
5. **上限**：`edits` 1~50 条；空列表或超限直接拒绝（防止模型一次塞几百条把审计撑爆）。
6. **返回**：`已编辑 N 处: <path>`，附每条 edit 的序号与替换次数（便于核对）。

**与 `edit_file` 的关系**：`edit_file` 保留不动（单点场景与既有测试/Profile 兼容），`multi_edit` 是批量入口；实现上可让 `edit_file` 内部委托 `multiEdit(path, [单个 edit])`，消除两份替换逻辑——但这是重构，不是本需求的前置条件。

## 五、迭代 3：web_fetch 网页正文抓取（P1）

### 5.1 接口

```java
@Tool(name = "web_fetch", description = "抓取网页并返回正文（HTML 转 Markdown），用于阅读搜索结果")
public String webFetch(
    @ToolParam(description = "http/https URL") String url,
    @ToolParam(required = false, description = "最大返回字符数，默认 20000") Integer maxChars)
```

### 5.2 执行流程（顺序即安全不变量）

```
参数校验（scheme 必须是 http/https）
  → sandbox.enforce(HTTP_REQUEST, url)
  → GET（超时 15s、最多 3 次重定向、手动跟随）
      → 每次重定向：对 Location 解析出的绝对 URL 再 enforce 一次
  → 检查 Content-Type
      text/html      → HTML 转 Markdown
      text/plain|md|json → 原样
      其他（二进制/图片/PDF） → 失败点名类型，不读 body
  → 有界读取（最多 2MB，超出即截断并提示）
  → 按 maxChars 截断 + 提示"已截断，可增大 maxChars"
```

### 5.3 关键决策

| 决策 | 选择 | 理由 |
|------|------|------|
| HTML 解析 | 引入 **jsoup**（唯一新增依赖） | 手写正则处理 `<script>`、嵌套标签、实体转义必然出错；jsoup 成熟、无传递依赖负担、体积小。需在父 POM 锁版本并过 depcheck |
| 转换粒度 | 保留标题、段落、列表、链接、代码块；剔除 `script/style/nav/footer/iframe` | 够模型阅读，不追求像素级还原 |
| 编码 | 优先 `Content-Type` charset，缺省 UTF-8，HTML 交给 jsoup 按 meta 探测 | 避免中文站点乱码 |
| 失败语义 | 非 2xx → `ToolResult.failure` 带状态码；4xx 不可重试，5xx/超时可重试 | 与 `http_get` 的"查询类失败可自救"一致 |
| 依赖 | 复用现有 `RestClient` + `Sandbox` | 不引入第二套 HTTP 客户端 |

### 5.4 安全注意

- **每次重定向都 enforce**：只校验初始 URL 会被 `302 → http://169.254.169.254/` 绕过；这是本需求唯一的高危点，harness 必须有专门用例。
- 不跟随 `file:`/`ftp:` 等非 http(s) scheme。
- 响应体有界读取，防止一个超大文件把堆打满。
- 内网地址拦截依赖 `WhitelistSandbox` 的域名策略（23/24 节），本工具只保证"调用 enforce 且不可绕过"。

## 六、迭代 4：todo_write 任务清单（P1）

### 6.1 接口

```java
@Tool(name = "todo_write", description = "创建或更新当前会话的任务清单（每次传全量列表）")
public String todoWrite(
    @ToolParam(description = "任务列表，整体替换旧清单") List<TodoItem> todos)

public record TodoItem(
    String content,        // 任务描述（祈使句）
    String status,         // pending | in_progress | completed
    String activeForm) {}  // 进行中时的展示文案，可选
```

### 6.2 行为规格

1. **全量替换语义**：每次传入完整列表，服务端整体覆盖——与 Claude Code `TodoWrite` 一致，避免增量合并带来的状态歧义。
2. **状态约束**：`status` 仅三值；**最多一个 `in_progress`**（0 个也允许），出现两个 → 拒绝并点名。
3. **渲染返回**：`[ ] 待办` / `[~] 进行中` / `[x] 已完成`，附 `已完成 2/5`；模型据此在下一轮知道自己走到哪。
4. **存储**：`TodoStore` 接口 + `InMemoryTodoStore`（按 `sessionId` 分桶），**本期不落库**；重启丢失是可接受边界，后续需要持久化时换实现、不改工具。
5. **上下文缺失**：拿不到当前会话/Profile → 失败点名，不静默写到全局。
6. **不做自动注入**：本期不把清单注入 system prompt（只在工具结果里回显）；"每轮提醒模型看清单"属于 PromptBuilder 的改造，另开需求。

### 6.3 为什么不做 todo_read

清单在每次 `todo_write` 的结果里完整回显，模型天然看得到；单独一个读工具只增加一次调用，没有信息增量。等未来清单需要跨会话/跨 agent 共享时再考虑。

### 7.2 每个迭代的测试清单

| 迭代 | 测试类 | 必测用例（守点） |
|------|--------|------------------|
| 1 分页 | `FileToolsTest` | 默认 2000 行 + 行号格式；offset/limit 区间；末页无提示；越界提示总行数；limit 夹上限；空文件；不存在点名路径；**10 万行文件返回字符数 < 200KB**（证明没整文件回传） |
| 2 批量 | `FileToolsTest` | 三处替换全部生效；**第 2 个 edit 失败 → 文件字节不变**；顺序依赖（先插入再改）；`replaceAll` 计数；多处匹配未开 replaceAll 报错；空列表/超 50 条拒绝；错误消息含"第 N 个" |
| 3 抓网页 | `WebFetchToolsTest` | 本地 `HttpServer` 返回 HTML → 标题/正文/链接保留、script/style 剔除；非 http(s) 拒绝且零请求；**302 跳到白名单外 → 第二次请求前被拦**；Content-Type 不支持 → 点名类型；超 2MB 截断；非 2xx 带状态码；`maxChars` 截断提示 |
| 4 清单 | `TodoToolsTest` | 全量替换（第二次调用后只剩新列表）；两个 in_progress 拒绝；空列表清空；非法 status 拒绝；会话隔离（A 的清单不影响 B）；渲染含三种状态符号与完成计数 |

```java

    assertThat(result.success()).isFalse();
    assertThat(Files.readString(file)).isEqualTo(original);  // 原子性：零写入
```

### 7.4 装配级验证

- `ReactAssemblyTest`：注册表按名能查到 `read_file` / `multi_edit` / `web_fetch` / `todo_write`；

## 八、做完怎么验（人工项）

harness 只能判"行为对不对"，下面这些必须人跑：

1. **分页的真实收益**：让模型读 `docs/TechnicalSolution.md` 的某一章，观察它是否主动用 `offset` 翻页、单次工具结果 token 是否显著下降。
2. **批量编辑的稳定性**：给一个"重命名一个字段（8 处）+ 改两处注释"的任务，确认一次 `multi_edit` 完成，且中途故意给一个错的 oldString 时文件未被破坏。
3. **抓网页的可用性**：`web_search` 拿到的链接直接喂给 `web_fetch`，确认模型能基于正文回答问题（而不是复述搜索摘要）。
4. **清单的约束力**：给一个 5 步任务，观察模型是否在每步完成后更新 `todo_write`、且同一时刻只有一个 `in_progress`。
5. **审计**：四次工具调用都在 `tool_invocations` 里可查（`trace_id` 可串起整轮）。

## 九、排期建议与依赖

```text
1. read_file 分页        ← 无依赖，先做（收益最大、风险最低）
2. multi_edit           ← 无依赖，可与 1 并行（同一文件，注意合并冲突）
3. todo_write           ← 依赖 Session 标识（18 节已就绪），实现最轻
4. web_fetch            ← 依赖 jsoup 引入 + 父 POM 锁版本 + depcheck 过；放最后
```

四件全部落在 `sableos-tool` 一个模块内，不改 `core` 契约、不加新模块——这是第 20 节"工具只是多写一个方法"设计的延续。`web_fetch` 是唯一需要新增第三方依赖的一件，走依赖评审时重点看 jsoup 的 CVE 与体积。

## 十、边界与遗留

- **不做 apply_patch**：理由见第一节；跨文件重构交给 MCP / 子 agent。
- **不做浏览器自动化**：JS 渲染、登录态、点击填表 → Playwright MCP。
- **不做视觉**：截图/看图依赖多模态模型与图像通道，另开需求。
- **不做工具按需加载**：工具数到 30+ 后再考虑 schema 懒加载 / tool search；当前 16 个尚在可控范围。
- **todo 不持久化**：重启丢失是本期明确边界；需要跨会话时换 `TodoStore` 实现，工具接口不变。
- **read_file 不做编码探测**：非 UTF-8 文件仍会失败；需要时另开"文档解析"工具（PDF/DOCX），不在读文件上堆功能。
